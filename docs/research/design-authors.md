# Design: authors

## Overview
Rainbird's own developer page promises knowledge authors can "export, diff, review in a pull request, and regression test in your CI process" — but the only sanctioned RBLang editing surface today is a legacy AngularJS Ace iframe inside Studio whose autocomplete is missing eight expression functions the engine has shipped since 2025. The field is empty: the sole prior VSCode extension (tom-sherman.rainbird-engineer-tools, 455 installs) has been abandoned since 2019 and contributes no language at all. This design makes VSCode the power-author surface Studio never had, for the BDO/EY/DAC Beachcroft-style knowledge engineer who has outgrown the code panel.

The thesis: text and git as source of truth is the strategic wedge, and everything in the MVP must run against today's real surface. That is achievable because Rainbird's richest editor assets are already extractable as a specification — the Studio bundle's structural validation schema (element nesting, attribute enums, validators), the rblint semantic checks, the context-aware completer, the 51-function expression catalogue, and the official snippet catalogue — and because the public Decisions API (GET /start, POST inject/query/response/undo, GET /analysis/evidence, POST /nl/explain) supports full query-with-evidence-tree loops from the editor. The .rbird export format is confirmed gzip-JSON containing the RBLang source, giving a lossless bridge to and from Studio with zero new platform work.

The design steals deliberately: Prisma-grade LSP polish as the five-star baseline; Regal's evaluate-codelens with convention-based input files for query running; Miragon's text-stays-source-of-truth graph webview for map visualization; Neo4j's connected-service intelligence; and it avoids the Salesforce anti-patterns (no config file required to activate, one extension, no subprocess sprawl).

What stays in Studio: official versioning and set-live administration, agent publishing, Co-author's Bedrock-EU-governed generation, stats, and casual visual editing. VSCode owns pro-code authoring, refactoring, multi-map repos, diff/PR review, local+CI regression testing, and evidence-driven debugging. Phase 2 layers on the undocumented surfaces (POST /maps upload, MCP served graphs) with honest labels; Phase 3 names the roadmap ask — a real map management API — that would close the loop entirely.

## Personas
- The Big-4 knowledge consultant (BDO/EY type): builds tax, audit and advisory decision services for multiple clients; semi-technical; needs multi-map repos, client handoff artifacts, and defensible review workflows
- The risk & compliance modeller (insurer/bank/law firm, DAC Beachcroft type): owns a regulated policy estate encoded in Rainbird; cares about audit trails, SME sign-off, and regression safety when policy changes
- The RBLang power author: the customer-side knowledge engineer who already lives in the Studio code panel and wants real editor ergonomics — keyboard-driven authoring, rename refactoring, search across maps, git
- The SME reviewer (secondary): a domain expert who never writes RBLang but must sign off changes — consumes semantic diffs in PRs and evidence-tree links rather than raw XML

## [MVP] RBLang Language Intelligence (LSP)  (surface: client-only, effort: L)
Full language service for RBLang that matches and then exceeds Studio's rblint + structural schema. Diagnostics: structural validation per Studio's own extracted validator table (element nesting rbl:kb>concept/rel/concinst/relinst/import/compound, required attributes, enums like askable=all|none|secondFormSubject|secondFormObject plus legacy true|false, concept behaviour mutually-exclusive|mutex|mx); rblint semantic checks (duplicate concinsts/facts, unknown concept/relationship types, subject-object type agreement, date/number/truth literal validity, datasource %S input typing); expression checks against the 51-function catalogue with left-to-right (non-PEMDAS) evaluation warnings, single-quote string enforcement, and a quick-fix suggesting countRelationshipInstances(...) is equal to 0 where authors attempt null tests; variable rules (%UPPER_SNAKE, %S/%O reserved, no custom variables in rule headers, warn on single-use variables); name character restrictions (no " ' \ < >, ≤2000 chars). Completions: context-aware per enclosing element like Studio's contextAwareCompleter, but including the 8 functions (includes, startsWith, endsWith, minObjects, maxObjects, isWithinRange, joinObjects, regexCount) the legacy Studio panel lacks. Hover docs for every element/attribute/function linking to docs.rainbird.ai .md pages. Go-to-definition and find-references for concepts, relationships, instances; F2 rename cascading across rels, rule conditions, datasource actions and question text; outline/breadcrumbs of concepts→rels→rules. Zero-config: activates on .rbl/.rblang files and on any XML whose root is <rbl:kb> — no config file, ever (the GraphQL/Apollo anti-pattern).
UX: Author opens a .rbl file (or Studio-exported XML): squiggles appear as they type with the exact wording style of Studio's validator ('X element has missing attribute: Y'), Ctrl+Space offers only the attributes valid in the current element that aren't already present, hovering 'minimumRuleCertainty' shows the default (20) and its cap relationship to cf, F2 on a concept renames it everywhere, and the Outline pane doubles as a mini map inventory. Problems panel totals mirror what Studio will accept on paste.
VSCode APIs: languages contribution + TextMate grammar (source.rblang with embeddedLanguages for expression scopes), vscode-languageclient / vscode-languageserver (LSP), DocumentSemanticTokensProvider, CodeActionProvider (quick fixes), RenameProvider / DefinitionProvider / DocumentSymbolProvider via LSP
Inspiration: Prisma LSP polish (the 5-star baseline: completion, hover, rename, quick-fix) + Regal diagnostics-as-you-type; spec sourced from Rainbird's own extracted Studio validator/rblint/completer
Risks: Studio assets are proprietary and publicly served but must be treated as a spec to reimplement, not code to copy (legal review). Grammar drift risk: changelog is unpublished after v4.106 while the engine is at 4.118. Compound element semantics are unknown — validate shape only, mark semantics unverified.

## [MVP] Run Query codelens with interactive decision sessions  (surface: public-api, effort: L)
The Regal-style 'evaluate this' affordance mapped to Rainbird's identical shape: a query is a goal (relationship) with subject/object slots. A codelens above every <rel> and every rule offers 'Run query' / 'Run against draft'. Execution uses the documented public API: GET /start/{kmID}?useDraft|version, POST /{sessionID}/inject, /query, /response, /undo. Convention-based inputs (Regal's input.json pattern): a sibling <mapname>.facts.json is injected automatically before the query (≤250 facts/batch). When the engine asks questions, the extension renders them faithfully to the question config: First Form as yes/no, Second Form with candidate concepts[] as picks, certainty slider when allowCF, 'unknown' option when allowUnknown, grouped extraQuestions[] as one form. Results show subject/relationship/object with certainty and factID; undo steps back one answer set. This is what makes VSCode better than Studio's Quick Query: the loop runs against the file you are editing (after sync) with your test facts versioned in git next to the map.
UX: Above '<rel name="speaks" ...>' a codelens reads 'Run query ▷ draft | v12'. Click → QuickPick asks for the subject (instances from the map offered as suggestions) → questions appear as a form in a side panel → result appears inline under the codelens ('French — 85%') and in a results panel with a 'Show evidence' button. A rainbird.facts.json next to the map is silently injected first, with a status-bar note '12 facts injected'.
VSCode APIs: languages.registerCodeLensProvider, window.createWebviewPanel (question form / results), QuickPick (window.showQuickPick), SecretStorage for X-API-Key, workspace.findFiles (facts.json convention discovery)
Inspiration: Regal 'Evaluate' codelens + convention-based input.json; GraphQL Inline Operation Execution's variable prompting
Risks: Queries run against the platform-side draft/version, not the local buffer — until push (Phase 2) or Studio paste-sync, the extension must show which kmVersion the session used (from /start response) to avoid stale-map confusion. Production result-returning queries are the billable unit on paid tiers — surface a counter.

## [MVP] Evidence Tree & Salience inspector  (surface: public-api, effort: M)
Rainbird's differentiator rendered natively in the IDE. After any query result (or from a pasted sessionID+factID), a webview builds the full evidence tree by recursively following condition factIDs via GET /analysis/evidence/{factID}/{sessionID} (x-evidence-key header; the JS SDK's fullEvidence() pattern). Nodes are colour-coded exactly as Studio: rule (dark blue), list-function (light blue), inject (light green), answer (red), datasource (dark green), map fact (orange) — with per-fact certainty, rule bindings (%S/%O/custom variables), and per-condition impact/salience/wasMet. A salience bar chart shows each condition's contribution. Crucially, clicking any rule node jumps to that rule's line in the RBLang file (matched by relationship type + Named Rule name) — evidence-to-source navigation Studio cannot do. Buttons: 'Explain in plain English' calls POST /nl/explain ({language, sessionID, factID}); 'Open in Studio' deep-links to [STUDIO_HOST]/evidence?id=[FACT_ID]&api=[API_HOST]&sid=[SESSION_ID] for sharing with SMEs.
UX: After a query returns 'high risk — 72%', the author clicks 'Show evidence': a tree panel opens beside the editor; expanding the top rule shows three conditions with impact 40/22/10; clicking the underweighted condition reveals the answer-sourced fact (red) that dragged certainty down; clicking the rule header jumps the editor to line 214 of the map. The salience chart makes the weight tuning conversation visual; /nl/explain produces a paragraph to paste into the client email.
VSCode APIs: window.createWebviewPanel with postMessage protocol, TextEditor.revealRange (evidence→source jump), env.openExternal (Studio deep link), SecretStorage (x-evidence-key)
Inspiration: Regal's DAP data-inspection instinct applied post-hoc; Neo4j result panels; Studio's own Evidence Tree/Salience Chart as the visual contract
Risks: Evidence requires the x-evidence-key or link-sharing enabled in Studio's Publish page — first-run flow must detect 403 and explain the toggle. /nl/explain is open beta with no SLA. Rule-line matching is heuristic when rules are unnamed (encourage Named Rules, v4.101+).

## [MVP] .rbird round-trip (Studio bridge)  (surface: client-only, effort: S)
The lossless, zero-new-platform-work bridge between Studio and git. The .rbird export format is confirmed gzip-compressed JSON ({format:'rbird', version:'1.1', studioData:{concepts x/y layout...}, unicronData:{rblang:[XML lines]...}}). Commands: 'Rainbird: Extract RBLang from .rbird' (gunzip, write the .rbl source file plus a sidecar layout file preserving studioData so graph positions survive); 'Rainbird: Package as .rbird' (repack current file + sidecar for Studio UI import — import into an existing map preserves the KMID). Opening a .rbird directly shows a read-only summary preview (map name, counts of concepts/rels/rules, README) with an 'Extract' button. This is how a BDO consultant gets a client map under version control today, and how edits get back into Studio's versioning flow without any undocumented API.
UX: Author drags an export from Studio into the repo; VSCode shows a preview tab 'Fraud Triage — 41 concepts, 67 rels, 118 rules' with [Extract RBLang]. One click yields fraud-triage.rbl (+ .rbird-layout.json committed alongside). After editing, 'Package as .rbird' produces the file they re-import via Studio's UI, which auto-lays-out any new nodes.
VSCode APIs: CustomReadonlyEditorProvider (rbird preview), commands.registerCommand, workspace.fs, Node zlib (desktop) / DecompressionStream (web build)
Inspiration: Miragon's text-as-source-of-truth stance; rbdat (Rainbird's own gunzip-JSON tool) proves the format
Risks: Format version drift (only v1.1 observed; identical since 2024). Exports exclude versions/tests/agents/stats — the extension must state what does not round-trip. Layout for newly added elements is delegated to Studio's auto-layout (graceful).

## [MVP] Connection manager & zero-friction onboarding  (surface: public-api, effort: M)
One-time, no-config-file platform connection powering every API feature. An AuthenticationProvider ('rainbird') stores the X-API-Key in SecretStorage and captures the environment: api.rainbird.ai (Community), enterprise-api.rainbird.ai, or custom {client}-api.rainbird.ai / self-hosted URL. A status-bar item shows environment + live engine version (GET /version, unauthenticated) — instantly flagging enterprise/community version skew. A walkthrough (Getting Started page) uses the published HelloWorld sandbox (public API key + KMID in Rainbird's docs) so a brand-new author runs their first query and sees their first evidence tree before they even have an account — the anti-Apollo move: value before configuration. Steps: open a sample map → run a query → view evidence → connect your account → extract your first .rbird.
UX: Install extension → Welcome walkthrough opens → step 2 'Run your first decision' executes a speaks-language query against the HelloWorld sandbox and pops the evidence tree. Accounts menu shows 'Rainbird: Community (4.118.0)'. Switching environment is a status-bar click. No settings.json required for any of it.
VSCode APIs: authentication contribution + authentication.registerAuthenticationProvider, ExtensionContext.secrets (SecretStorage), window.createStatusBarItem, walkthroughs contribution with completionEvents (onCommand)
Inspiration: Neo4j connection management + status bar; Terraform's bundled zero-install activation; GraphQL/Apollo config-required activation as the named anti-pattern
Risks: API keys are user-scoped and powerful — never write them to settings; enterprise SSO environments may need the key from the Studio Publish page, so the walkthrough must show where it lives. HelloWorld sandbox key is published by Rainbird but could rotate.

## [MVP] Decision test explorer (Studio automated tests in the IDE)  (surface: public-api, effort: L)
The regression-testing half of the 'regression test in CI' promise, for the author's inner loop. Studio's Automated Tests export/import as JSON (docs: 'changes can be made easily in a text editor'), and each test is a recorded query + scripted answers + expected results — all executable via the public Decisions API (start→inject→query→response loop, compare result certainty/objects). The extension contributes a TestController that discovers tests/*.rbtest.json files by convention, shows them hierarchically per map in the Test Explorer, and runs them against draft or a chosen version. Failures render TestMessage diffs ('expected: eligible 80%, actual: eligible 45%') with a one-click 'Show evidence' on the actual result — turning every red test into a debuggable decision. Supports Studio's two modes (results-only via inject vs end-to-end answering) and continuous runs on file save. The same JSON format seeds the CI runner (engineer lens), so tests written here run in the pipeline unchanged.
UX: Author opens the repo: Test Explorer lists 'R&D Tax Relief › 24 scenarios'. They tweak a rule weight, hit the continuous-run eye icon; three tests go red with certainty diffs; clicking one opens the evidence tree for the failing scenario; the salience chart shows the over-corrected weight. Green again → commit map + tests together.
VSCode APIs: tests.createTestController + TestItem/TestRun/TestMessage, TestRunProfile (Run kind, supportsContinuousRun), workspace.createFileSystemWatcher (test discovery)
Inspiration: Kogito SceSim scenario editor + Apex Test sidebar + OPA workspace tests; Regal's inline expected/actual discipline
Risks: The exported test JSON schema is a user-visible artifact but formally undocumented — pin to observed format, fail gracefully on unknown fields. Tests execute against platform draft, not local buffer (same sync caveat as query running; solved fully by Phase 2 push / Phase 3 sync). Each result-returning run counts toward contractual query limits on paid tiers.

## [MVP] Studio-parity snippets & bulk authoring commands  (surface: client-only, effort: S)
Immediate-parity quick win that supersedes the abandoned 2019 incumbent. Ships the full snippet catalogue mirroring Studio's own ace/snippets/rblang set: relinst rule/fact, condition (rel, expression, expression+value), concept, rel with all three question-form children, concinst (+markdown meta), the three datasource variants (GET, POST+CDATA, headers), import, compound, and expression skeletons for sumObjects/countRelationshipInstances/isSubset. Adds the incumbent's proven generators as first-class commands: 'Create concinsts from list' (paste names, pick concept type), 'CSV → facts' (column mapping to subject/relationship/object/cf triples, honoring cf default 100), and 'New knowledge map' scaffolding the rbl:kb skeleton with recommended element order (concepts → rels → instances → facts → rules).
UX: Typing 'rule' + Tab expands a relinst with condition placeholders and tab stops through type/cf/weight; 'Rainbird: CSV → facts' turns a client's spreadsheet of 400 entity facts into valid relinst lines in seconds — the exact task that made consultants love the old extension.
VSCode APIs: snippets contribution point, commands.registerCommand + QuickPick, WorkspaceEdit / TextEditor.edit
Inspiration: tom-sherman.rainbird-engineer-tools (its createFactsFromTable was the whole extension's value); Studio's official Ace snippet catalogue as the canonical list
Risks: Minimal; keep snippet bodies in lockstep with the LSP's schema so snippets never insert what the linter flags.

## [Phase 2] Knowledge-map graph view (text stays source of truth)  (surface: client-only, effort: L)
A webview panel rendering the parsed map as an interactive graph — concepts as typed nodes (string/number/date/truth badges), relationships as directed edges, rule counts as badges per relationship, datasource indicators on subject concepts. The RBLang text remains the single source of truth (Miragon's exact stance): the graph re-renders on document change, and clicking any node/edge reveals the corresponding line in the editor. Uses the committed .rbird-layout.json sidecar for node positions when present (so the view matches what the author sees in Studio) and falls back to auto-layout (ELK/dagre) otherwise. Filter box ('show everything within 2 hops of "transaction risk"'), certainty-query affordances (right-click a rel → Run query), and SVG export for governance packs. A keyboard toggle flips between diagram and raw XML like Miragon's Ctrl+Shift+E. Graph-gesture editing (drag to create a rel, writing a WorkspaceEdit back to text) is a deliberate later increment — read-and-navigate first, matching what authors actually miss when they leave Studio.
UX: Author hits the 'Open map view' editor-title icon: split view with graph right, XML left. They click the 'KYC risk' node — editor jumps to the concept; they filter to its neighbourhood to explain the model in a client workshop; File > export SVG drops the diagram into the audit pack.
VSCode APIs: window.createWebviewPanel (or CustomTextEditorProvider with priority:option for a 'Map View' open-with), workspace.onDidChangeTextDocument (live re-render, echo-guarded), TextEditor.revealRange, asWebviewUri + CSP
Inspiration: Miragon BPMN Modeler ('the text file stays the source of truth', Ctrl+Shift+E toggle) + Neo4j Viz webviews + hediet/vscode-drawio two-way sync precedent
Risks: Graph-library licensing needs checking (bpmn-js-style watermark constraints); large maps (Foundry-scale policy estates) need virtualization; full graph editing parity with Studio is a trap — scope discipline is the feature.

## [Phase 2] Semantic diff & PR review lens  (surface: client-only, effort: M)
The 'review in a pull request' promise made real for SMEs who cannot read XML diffs. A model-level comparison of two RBLang documents (working tree vs HEAD, or any two git revisions via the git extension's timeline) producing a categorized change report: concepts added/removed/retyped, relationships with changed askability/plurality/question wording, rules with changed conditions, weights, cf, minimumRuleCertainty, or evidence text — rendered as a webview and exportable as a markdown summary to paste into the PR description ('Rule "High risk counterparty" [Named Rule]: condition weight 100→60; added optional condition on "sanctions list match"'). Inline in the editor, a gutter/codelens marks changed rules since HEAD. This is the feature that converts a compliance sign-off from 'trust me' to a reviewable artifact — and it needs zero platform surface.
UX: In the Source Control view, right-click fraud-map.rbl → 'Rainbird: Semantic diff vs HEAD'. A panel lists 3 rule changes and 1 new relationship, each linking to side-by-side text. 'Copy summary as markdown' goes into the PR body; the SME reviewer approves without opening the XML.
VSCode APIs: git extension API (vscode.git) for revision content, TextDocumentContentProvider (rainbird-diff: scheme), window.createWebviewPanel, FileDecorationProvider / gutter decorations (DecorationRenderOptions)
Inspiration: Miragon's element-level diagram diff with color coding; Prisma's model-aware mindset applied to review
Risks: Diffing depends on stable element identity — unnamed rules must be matched heuristically by type+conditions (another push toward Named Rules). Keep output deterministic so CI can regenerate the same summary (shared format with the engineer-lens CI tooling).

## [Phase 2] @rainbird Copilot chat participant (Co-author analog in the IDE)  (surface: client-only, effort: L)
GenAI-assisted authoring in the editor, mirroring Co-author's Plan/Edit/Ask modes as slash commands, but with a verification loop Studio's Co-author doesn't expose: every generated block is validated by the local LSP before it is offered. Commands: /draft (generate map skeleton or rule set from pasted/attached policy text using lm.selectChatModels, prompted with the RBLang authoring guide and validation checklist — the same self-correction pattern as Rainbird's own Noesis validate_stage prompts and the Claude Skill's 'fixes syntax errors automatically'); /edit (targeted change to the current selection: 'make this rule top-down-strict and add an optional condition on residency'); /explain (plain-English narrative of a selected rule/expression — offline complement to /nl/explain, which needs a live session); /docs (grounded answers from docs.rainbird.ai's llms.txt + .md corpus, which Rainbird explicitly built for agent consumption). Responses stream RBLang with 'Apply edit' buttons that write WorkspaceEdits. Positioning next to official Co-author is explicit: Co-author (Bedrock, EU processing, ISO27001) remains the sanctioned path for sensitive client documents; @rainbird uses the author's own Copilot subscription and is best for syntax-level assistance and repo-local iteration.
UX: Author selects a policy paragraph in a markdown file, types '@rainbird /draft rules for this using concepts from fraud-map.rbl' — the participant reads the open map for existing concept/rel names (no invented vocabulary), streams a rule block, shows '2 lint issues auto-corrected', and offers [Insert at cursor]. '@rainbird /explain' on a gnarly isSubset expression returns a sentence the author pastes into the rule's alt evidence text.
VSCode APIs: chatParticipants contribution + chat.createChatParticipant, ChatResponseStream (markdown, command buttons, references), lm.selectChatModels + LanguageModelChat.sendRequest (@vscode/prompt-tsx), workspace.applyEdit
Inspiration: @mongodb chat participant with /query /schema /docs; Noesis/Claude Skill lint-and-self-correct loop; Prisma's Copilot docs participant
Risks: Requires Copilot (free tier exists but is limited). Data governance: client policy text goes through the user's Copilot model, not Rainbird's EU Bedrock — must be stated in-product. Hallucinated syntax is mitigated but not eliminated by the lint loop; generated rules still need SME review (the PR diff lens completes the story).

## [Phase 2] Push map to platform (graph upload)  (surface: undocumented-api, effort: M)
Closes the edit→run gap: pushes the current RBLang file to the platform so codelens queries and tests exercise exactly what's in the buffer. Uses POST https://api.rainbird.ai/maps — the non-public graph-upload endpoint confirmed in Rainbird's NoesisAPI source and relied on by the Claude Skill and RAKE. Today its observed semantics are create-only ('every graph update creates a new graph in your account'), so the extension treats pushed maps as disposable scratch graphs: 'Push & Query' creates a scratch graph, runs the session against it, and offers cleanup guidance; the returned kmID is remembered per file. The documented fallback (package as .rbird → Studio UI import, which preserves KMID) remains one click away and is the recommended route into governed versioning. If/when Rainbird blesses an update-in-place contract, this feature upgrades transparently to true draft push.
UX: Author hits 'Push & Query' in the editor title: status bar shows 'Uploading… scratch graph created', the query codelens now targets the scratch graph, and the evidence tree reflects the local edit made 30 seconds ago. A workspace notification lists scratch graphs created this session with an 'open Studio to delete' link.
VSCode APIs: commands.registerCommand, workspace state (Memento) for file→kmID mapping, window.withProgress
Inspiration: Rainbird's own Claude Skill build-upload-test loop, brought into the author's editor; Miragon's deployment sidebar
Risks: Highest-risk dependency in the design: endpoint is unofficial, contract and auth behaviour may change without notice, and create-only semantics churn kmIDs (never wire integrations to scratch graphs). Needs internal Rainbird blessing before GA; feature-flag it and degrade to the .rbird route. Account clutter from scratch graphs must be actively managed.

## [Phase 2] Served-graph MCP integration & agent-mode tools  (surface: undocumented-api, effort: M)
Two AI-consumption surfaces. (1) MCP: Rainbird's research preview serves any published graph as a Streamable-HTTP MCP endpoint exposing describe_graph/inject/query/answer/explain tools. The extension contributes an McpServerDefinitionProvider so the author pastes their served-graph URL once (stored in SecretStorage — the URL is self-authenticating and must be treated like a password, never written to mcp.json or settings), and the graph's tools become available to Copilot agent mode and any MCP-capable client in VSCode. The author can then ask an agent to probe their own model ('query this graph for a 17-year-old applicant and summarise the follow-up questions'). (2) Native LM tools for agent mode regardless of MCP: rainbird_validate_map (runs the local linter over a file), rainbird_run_query (documented Decisions API), rainbird_get_evidence (evidence fetch + summarise) — letting Copilot agents lint-fix-test RBLang autonomously inside the workspace, the same loop the Rainbird Claude Skill performs externally.
UX: Command 'Rainbird: Connect served graph (MCP)' prompts for the URL with a secrecy warning, verifies with describe_graph, and shows the generated capability manifest (queryable relationships, key concepts) in a panel. In Copilot agent mode the author types 'run our standard KYC scenarios against the served graph and flag any instance names it silently ignores' — catching the documented footgun where unrecognized instances are accepted silently.
VSCode APIs: mcpServerDefinitionProviders contribution + lm.registerMcpServerDefinitionProvider (McpHttpServerDefinition), languageModelTools contribution + lm.registerTool (invoke/prepareInvocation), SecretStorage
Inspiration: Prisma/Terraform MCP servers; VSCode MCP GA (1.102) mechanics; Rainbird MCP preview tool set (describe_graph/inject/query/answer/explain)
Risks: Research-preview surface under the RAKE umbrella — endpoints can be paused/removed and the contract may shift. explain requires the graph's Evidence Tree Link toggle (Studio → Publish → API Management), so detect and explain the error. URL secrecy is a real operational risk; the extension must actively prevent the URL landing in shareable config.

## [Phase 3] Workspace & linked-map intelligence  (surface: client-only, effort: M)
Multi-map repos as first-class citizens — the thing Studio structurally cannot do. Workspace-wide indexing of every RBLang file: search for a concept across a client's whole estate, workspace symbols, cross-map find-references. Resolves <import km="..." versionNumber="..."/> (a confirmed, Studio-supported but undocumented linked-map feature — Studio serializes it and its linter resolves imports via an internal editorResources endpoint) against sibling files in the workspace via an explicit km-id↔file mapping (a comment header or workspace map registry), enabling completions and go-to-definition for imported concepts/relationships and import-aware duplicate/type diagnostics — the local equivalent of Studio's import-resolving lint. Platform-hosted imports that aren't in the workspace surface as 'unresolved dependency' diagnostics (DEPSREQUIRED analog) with a note that resolving them from the platform needs the roadmap management API.
UX: Consultant opens the 'BDO tax estate' repo (9 maps). Cmd+T 'trading status' finds the concept in the shared base map; a specialist map importing it shows its rels in completions; renaming in the base map warns about 3 dependent maps. The Explorer badge flags one map importing a versionNumber that no local file matches.
VSCode APIs: LSP workspace folders + workspace symbols, workspace.createFileSystemWatcher, FileDecorationProvider (unresolved-import badges)
Inspiration: Terraform module resolution + GraphQL multi-project config (minus the mandatory config file); Studio's own import-resolving rblint as the behavioural spec
Risks: import is engine-supported but absent from public docs — confirm ongoing support internally before promoting it in UX. km-GUID↔file mapping is convention-based; keep it in-file (comment) so it survives git operations.

## [Phase 3] Decision Replay debugger (DAP)  (surface: public-api, effort: XL)
Step-through debugging of a decision after it runs — an Apex-Replay-style debugger rather than live engine stepping (the engine exposes no live trace; evidence is post-hoc). 'Debug this query' runs the session, then reconstructs a stepped execution from two public sources: the recursive evidence tree (rule bindings, per-condition impact/salience/wasMet) and GET /analysis/interactions/{sessionID} (start/inject/query/question/answer/result/datasource event log with timestamps). The DAP session presents the backward-chaining goal stack as the call stack (goal → rule → subgoal), variables panes for %S/%O/custom bindings and condition outcomes, and honors breakpoints set on rule lines — replay pauses when that rule fires. Stepping follows the Match→Infer→Ask resolution order per condition. This makes the engine's reasoning tangible for authors debugging 'why did certainty come out at 45%?' beyond what the static evidence tree shows.
UX: Author sets a breakpoint on the 'eligible for relief' rule, clicks 'Debug query' codelens, answers the questions; the debugger then replays: call stack shows the goal chain, stepping into a condition shows the datasource event that supplied the fact and its certainty; the breakpoint hits when the suspect rule fires with bindings visible.
VSCode APIs: debuggers + breakpoints contribution points, @vscode/debugadapter with inline DebugAdapterDescriptorFactory, DebugConfigurationProvider (dynamic launch configs), languages.registerCodeLensProvider ('Debug query')
Inspiration: Regal's DAP debugger (breakpoints/stepping over rules) + Salesforce Apex Replay Debugger (log-based reconstruction) + JOT 2023 DSL-DAP reinterpretation
Risks: Interaction recording is OFF by default and enabled per KM version in Studio — the debugger must detect this and guide the toggle; only sessions started after enabling are recorded. Replay fidelity of MIA ordering is partially inferred — label it 'replay', never 'live'. Validate demand first: the Evidence inspector may already cover 80% of the need at 20% of the cost.

## [Phase 3] Maps & versions sidebar (pull/push/publish workflow)  (surface: roadmap, effort: XL)
The full text-as-source-of-truth loop, honestly labelled as needing new platform work. A 'Rainbird' activity-bar view listing the account's knowledge maps, each with its draft + immutable numbered versions and Live flag; actions: pull draft into the workspace as RBLang, push the workspace file to draft, create a version, set a version live, and open Studio deep-links — making 'git is the master, Studio is the runtime console' real.
