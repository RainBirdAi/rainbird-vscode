# Design: internal

## Overview
For Rainbird's own engineers, the VSCode extension is not a convenience — it is the missing delivery mechanism for promises the company already sells. rainbird.ai/developers claims "export, diff, review in a pull request, and regression test in your CI process"; pricing sells "Graded evals in your CI" and "ModelOps: who changed what, when and why"; the Community tier promises 25+ accelerators with "locally runnable evals." None of this has software behind it today: the only sanctioned RBLang editor is a legacy AngularJS Ace iframe whose autocomplete lags the engine by ~26 functions, the public changelog stopped at 4.106 while production runs 4.118, and the only map-upload path is an undocumented POST /maps endpoint used by the Claude Skill and Noesis. The design thesis is therefore threefold. (1) Make the extension the internal production line for accelerators: a scaffolded repo convention, a Test Explorer eval harness whose core doubles as a headless CI runner, corpus-wide lint reimplemented from Studio's own embedded validator table, and transparent .rbird handling — so solution engineers build, grade, and regression-test all 25+ accelerators in git before customers ever see them. (2) Make the extension the dogfooding ring that hardens undocumented surfaces into public contracts: POST /maps upload, the rake.rainbird.ai MCP graph-serving preview, and an engine-version compatibility database that doubles as the changelog Rainbird stopped publishing. Pre-release channel = internal ring; stable channel = public-api-only surface. (3) Treat three launch decisions as first-class deliverables: publish under a domain-verified `rainbird` publisher and supersede the abandoned 2019 tom-sherman extension; open-source the language core (LSP, schema, grammar, .rbird codec) to make "you can leave with your logic at any time" credible; and dual-publish to Marketplace and Open VSX so the Cursor/Claude Code audience RAKE targets can actually install it. Every MVP feature below runs against today's documented Decisions API or pure client-side code; undocumented and roadmap dependencies are labelled honestly, because the extension's second job is to generate the internal pressure that turns them into supported platform surface.

## Personas
- Solution/knowledge engineer building and maintaining the 25+ use-case accelerators (KYC, transaction monitoring, prior auth...) who needs locally runnable, gradable evals and a repeatable repo layout
- Platform/core engineer (Norwich team of ~18) who debugs customer sessions, owns engine releases 4.107-4.118 with no public changelog, and needs corpus-wide lint/compat checks against real customer maps
- Rainbird Labs engineer (RAKE, Claude Skill, Rule Tracker) who dogfoods the undocumented POST /maps upload and the rake.rainbird.ai MCP graph-serving preview and needs them pressure-tested toward public contracts
- Product/DevRel leadership treating the extension as a strategic product surface: publisher identity, open-source posture, distribution reach (Marketplace + Open VSX + Cursor), and the extension as the delivery channel for developer-facing promises already on the pricing page

## [MVP] Eval & Regression Harness (Test Explorer + headless CI runner)  (surface: public-api, effort: L)
Makes 'Graded evals in your CI' (sold on rainbird.ai/pricing, undocumented anywhere) real. Workspace files matching **/*.eval.json — a documented superset of Studio's Automated Tests JSON export format so suites round-trip with Studio import — appear as runnable tests. Each scenario executes the documented Decisions API loop: GET /start/{kmID}?useDraft|version → POST /{sessionID}/inject (≤250 facts) → POST /{sessionID}/query → scripted POST /{sessionID}/response answers → assert result triple + certainty (with tolerance bands, e.g. 'certainty ≥ 80'). The identical runner core ships as a headless npm bin (npx @rainbird/evals) emitting JUnit XML + a JSON grade report with nonzero exit on failure — one GitHub Action away from CI. This is the tool every solution engineer needs to ship the 25+ accelerators with regression coverage, and the Claude Skill's exported JSON test suites plug straight in.
UX: Rainbird beaker icon in the Test Explorer. Suites appear hierarchically (suite → scenario → assertion) with lazy discovery. Click run: status bar shows the target environment (Community/Enterprise/custom base URL from the auth session); pass/fail with expected-vs-actual diff rendered via TestMessage, and a 'View evidence' link on each failed assertion that opens the result's evidence tree (GET /analysis/evidence/{factID}/{sessionID}). Eye icon enables continuous runs on file save. A 'Copy CI workflow' code action drops a ready .github/workflows/rainbird-evals.yml.
VSCode APIs: tests.createTestController, TestRunProfile (Run kind, supportsContinuousRun), TestMessage.diff, workspace.createFileSystemWatcher, authentication.getSession, ExtensionContext.secrets
Inspiration: OPA 'Run Tests in Workspace' + Apex Testing sidebar + Kogito SceSim scenario editor; convention-based discovery from Regal's input.json pattern
Risks: The Studio Automated Tests JSON schema is not publicly documented (internal knowledge closes this); every result-returning query is the billable unit, so heavy eval runs consume quota — needs a fair-use note and result caching; session TTL semantics are undocumented.

## [MVP] Accelerator Workspace Scaffold  (surface: client-only, effort: M)
One command stamps out the standard accelerator repo: map.rbl, evals/smoke.eval.json, fixtures/, README.md with requirement-to-rule traceability table (the Claude Skill's documented pattern), and the CI workflow. Standardising the layout across the 25+ accelerators is what makes the Community-tier promise 'download the accelerator, run the evals locally' true in one gesture, and gives internal solution engineers a single convention instead of ad-hoc exports. Zero mandatory config files — everything is convention-discovered (the GraphQL/Apollo config-file requirement is the documented anti-pattern).
UX: Command palette: 'Rainbird: New Accelerator…' → QuickPick of templates (blank, eligibility pattern, datasource-backed, mirror of a Library pattern) → folder created and a Walkthrough opens: step 1 write a concept (completionEvents onCommand), step 2 run the smoke eval, step 3 wire CI. viewsWelcome content in the empty Test Explorer links 'Scaffold an accelerator' when a .rbl file exists but no evals do.
VSCode APIs: commands.registerCommand, walkthroughs contribution, viewsWelcome contribution, window.showQuickPick, workspace.fs
Inspiration: Regal/OPA convention-over-config; VS Code walkthrough onboarding pattern
Risks: Template drift vs Studio Library content unless the scaffold templates are generated from the same source the Library uses.

## [MVP] Corpus Lint + Bulk Codemods (rblint parity, SARIF out)  (surface: client-only, effort: M)
Workspace-wide 'Rainbird: Lint All Maps' reimplementing — as a clean-room spec, per legal review — the checks in Studio's embedded validator (module-1579 element/attribute/enum table) and the legacy rblint worker: duplicate concinsts/facts, unknown concept/relationship references, subject-object type agreement, date/number/truth literal validity, datasource %S input binding, unresolved <import km@versionNumber> deps (DEPSREQUIRED), weight-sum-zero rules, and the silent-footgun of instance names that match nothing. Companion codemods fix at scale: normalize allowCf→allowCF, migrate legacy askable=true|false to enum values, quote relationship names in list functions per current docs, flag <compound> (validator-tolerated but Studio-unmodelled), rename a concept/relationship across every map AND eval file. CLI mode emits SARIF for GitHub code scanning. This is the internal corpus tool: run it over all accelerators, Library templates, and customer-exported maps in support tickets.
UX: Problems panel fills with per-file diagnostics; each fixable rule offers a lightbulb quick-fix and a 'Fix all in workspace' code action. Renames use F2 on any concept/rel name and preview via the standard refactor preview panel. In CI: npx @rainbird/lint --sarif produces annotations on PRs of the accelerator monorepo.
VSCode APIs: languages.createDiagnosticCollection, CodeActionProvider (QuickFix + SourceFixAll), RenameProvider, workspace.applyEdit / WorkspaceEdit, workspace.findFiles
Inspiration: Regal per-rule quick-fix code actions; Prisma rename-with-reference-updating
Risks: Extracted Studio assets are proprietary though publicly served — must be treated as a specification to reimplement, not code to copy (flagged for legal); the <compound> element's runtime semantics remain unknown even internally-documented, so lint can only warn, not validate.

## [MVP] .rbird Codec + Git Diff Integration  (surface: client-only, effort: S)
Studio exports are gzip-compressed JSON ({format:'rbird', studioData(layout), unicronData.rblang[]}) — opaque to git, which breaks the 'export, diff, review in a pull request' promise at the first step. Commands 'Extract RBLang from .rbird' and 'Pack .rbird' round-trip losslessly, preserving studioData x/y layout so re-import into Studio keeps graph positions. 'Configure Git for Rainbird' writes .gitattributes with a textconv diff driver so PRs and git log -p show RBLang diffs of binary exports directly. Internal payoff: support engineers open any customer-attached .rbird instantly; the accelerator pipeline can commit either format.
UX: Double-clicking a .rbird file opens a read-only preview (extracted RBLang with a header note and an 'Extract to editable file' button) via a custom editor. Explorer context menu carries Extract/Pack. The git setup command shows a diff of the .gitattributes/.git/config changes before applying.
VSCode APIs: window.registerCustomEditorProvider (readonly CustomEditorProvider), commands.registerCommand, menus contribution (explorer/context), workspace.fs
Inspiration: Miragon 'text file stays the source of truth'; rbdat (Rainbird's own trivial gunzip pretty-printer) proves the format
Risks: .rbird format version is 1.1 today with no compatibility guarantee; layout-preserving pack needs fixtures from real Studio exports (available at /tmp/rblang/).

## [MVP] Map Upload via POST /maps (Labs dogfood ring)  (surface: undocumented-api, effort: M)
The single most strategic dogfooding surface. 'Rainbird: Upload Map to Account' POSTs the active RBLang document to https://api.rainbird.ai/maps with headers X-API-Key + Version: v1 and JSON body {rblang, name, description} — the exact contract verified in the NoesisAPI source and used by the Claude Skill. Create-only today (every upload makes a new map, mirroring the Skill's documented limitation), so the extension names uploads deterministically (fileBasename@gitShortSha) and immediately offers 'Run evals against the new kmID'. Server-side validation errors are parsed back into editor Diagnostics — turning the platform's own parser into the ultimate linter. Internal engineers using this daily generate exactly the pressure and bug reports needed to graduate /maps into a documented public endpoint with update-in-place semantics.
UX: Command palette + editor title button on .rbl files, visibly badged 'Labs — undocumented API' and gated behind setting rainbird.labs.enableUpload (default on in the pre-release ring, off in stable). On success: toast with kmID, 'Copy kmID', 'Start draft session', 'Run evals'. On 4xx: squiggles at the offending lines where the error payload permits, else a parsed error list in a peek view.
VSCode APIs: commands.registerCommand, languages.createDiagnosticCollection, authentication.registerAuthenticationProvider (X-API-Key session), ExtensionContext.secrets, window.withProgress
Inspiration: Miragon deployment sidebar (deploy BPMN from editor); Salesforce deploy-on-save done right (single fast HTTP call, no CLI subprocess sprawl)
Risks: Endpoint is unversioned and could change without notice (that is partly the point of dogfooding it); create-only floods accounts with maps — needs naming discipline and a cleanup story; error payload shape for line mapping is unverified.

## [MVP] Publisher Identity & Incumbent Supersession (launch decision)  (surface: client-only, effort: S)
Publish under a new domain-verified `rainbird` publisher (Rainbird Technologies Ltd, verified against rainbird.ai) using Entra ID federation for publishing since global Azure DevOps PATs retire Dec 2026. The only prior art is tom-sherman.rainbird-engineer-tools — 455 installs, abandoned since June 2019, personal unverified publisher, contributing no language/grammar at all — plus his vscode-coffeebird. Both are MIT. Decision: contact Sherman (near-certainly an ex-Rainbird engineer, Norwich-based) for a deprecation notice pointing at the official extension; absorb his 11 snippet prefixes verbatim for muscle-memory compatibility (MIT permits it); do NOT copy extracted Studio assets (Ace mode, rblint, snippet catalog, structural schema) — reimplement from them as spec, with legal sign-off recorded.
UX: Marketplace listing shows the verified-domain checkmark; extension README carries a migration note for rainbird-engineer-tools users; the old extension (if Sherman cooperates) shows a deprecation banner with an install link. Search for 'rainbird' or 'rblang' surfaces the official extension first.
VSCode APIs: @vscode/vsce publish, Marketplace publisher domain verification, extensionPack/extensionDependencies (none — single extension, explicitly avoiding the 18-extension Salesforce anti-pattern)
Inspiration: Salesforce anti-pattern (fragmentation) inverted; Prisma single-extension polish
Risks: Sherman may be unreachable (deprecation of his listing then can't be forced); marketplace name squatting risk if delayed.

## [MVP] Open-Source Language Core + Canonical Schema (launch decision)  (surface: client-only, effort: M)
Split the codebase: `rblang-language-server` (LSP, TextMate grammar, structural schema as machine-readable JSON, rblint rules, .rbird codec, eval-runner core) published Apache-2.0 in a public repo; the Marketplace extension is a thin shell adding platform-connected features (auth, upload, session forensics). Rationale for the company: (a) makes 'You can leave with your logic at any time' (pricing page) technically credible — the format tooling outlives the vendor; (b) the xmlns namespace URI http://rbl.io/schema/RBLang is domain-squatted (TLS cert now CN=neronote.com) — publish the canonical schema at a Rainbird-controlled URL and reference it from the OSS repo, quietly fixing an embarrassment; (c) revives developer trust after the archived RainBirdAi GitHub org; (d) invites the coffeebird-style community that already existed once. Internal engineers get the same benefit as external: the language core becomes a dependency RAKE, Studio, and the Claude Skill can all consume instead of four divergent validators (Studio module-1579, legacy rblint, Noesis prompts, Skill checks).
UX: Not user-facing per se; the extension's README links the OSS repo; 'RBLang schema' hover cards cite the canonical schema URL. Issues for language bugs land in the public tracker, platform bugs in the internal one.
VSCode APIs: vscode-languageclient v10 (bundled server, zero-install activation), languages + grammars contribution points
Inspiration: Regal (open LSP, Apache-2.0) and Prisma (open language tools, proprietary cloud); Drools as the cautionary tale — a half-committed LSP dies, so OSS must come with ownership
Risks: Maintenance commitment with an 18-person company; schema publication makes grammar changes a public compatibility contract (arguably a feature — it forces the changelog discipline back).

## [MVP] Marketplace + Open VSX Dual Publishing with Release Rings (launch decision)  (surface: client-only, effort: S)
Publish to both the VS Code Marketplace and Open VSX from day one — searches for rainbird/rblang/coffeebird on open-vsx.org return empty today, and Open VSX is what Cursor, Windsurf, VSCodium, code-server, and Gitpod resolve. The RAKE/Claude Skill audience skews heavily toward Cursor and Claude Code, so Open VSX is not optional reach, it is the primary channel for the exact developers Rainbird courts. Ring strategy: vsce publish --pre-release (odd-minor convention) is the internal dogfood ring where Labs features ship first (POST /maps upload, MCP serving, compat DB updates for unreleased engine versions); the stable ring exposes only public-api surface. CI publishes both registries from one pipeline.
UX: Internal engineers install the pre-release channel via the Marketplace 'Switch to Pre-Release Version' button; external users on stable never see Labs commands unless they opt into the setting. Cursor users install from Open VSX transparently.
VSCode APIs: vsce publish --pre-release, ovsx publish, when-clause contexts gating Labs commands (contributes.commands enablement)
Inspiration: Terraform/Prisma bundled-and-stable vs pre-release cadence; Open VSX gap identified in incumbent audit
Risks: Open VSX requires separate namespace claim + Eclipse publisher agreement; keeping two registries in version lockstep needs CI discipline.

## [Phase 2] Engine-Version Compatibility Lint (the changelog that stopped)  (surface: public-api, effort: M)
The public changelog ends at 4.106.0 (Mar 2026) while production serves 4.118.0 — twelve undocumented releases — and self-hosted/on-prem Kubernetes customers pin old engines. Ship a versioned feature database in the OSS repo mapping RBLang surface → minimum engine version (regexCount ≥4.95, Named Rules name attr ≥4.101, multi-operator brackets ≥4.101, the 51-function catalogue with introduction versions; post-4.106 entries maintained by the platform team, since only they know). The extension fetches GET {base}/version (unauthenticated, documented) for the configured target environment and raises diagnostics when a map uses features newer than the target. Internal payoff is double: solution engineers stop shipping accelerators that break on a customer's pinned engine, and maintaining the DB forces the platform team to re-institute changelog discipline — the DB becomes the de-facto public changelog.
UX: Status bar item: 'Rainbird 4.118 (Community)' — click to switch target env or pin a version. Using a too-new function underlines it: 'regexCount() requires engine ≥4.95; target is pinned at 4.90 (customer: on-prem)'. A 'Compatibility report' command tabulates every versioned feature used across the workspace.
VSCode APIs: window.createStatusBarItem, languages.createDiagnosticCollection, workspace configuration (rainbird.targetEngine), fetch from extension host
Inspiration: Terraform 'enhanced validation based on detected provider versions'; Neo4j lint auto-matched to connected DB version
Risks: Feature DB accuracy for 4.107–4.118 depends entirely on internal cooperation; wrong data is worse than none.

## [Phase 2] Session Forensics: Interaction Log + Evidence Explorer  (surface: public-api, effort: L)
The internal debugging workflow for 'why did this customer decision come out wrong'. Paste a sessionID (from a support ticket or Studio stats) and the extension pulls GET /analysis/interactions/{sessionID}?format=json (x-interaction-key), GET /analysis/session/{sessionID}?filter=facts|version (X-API-Key), and recursively walks GET /analysis/evidence/{factID}/{sessionID} (x-evidence-key) to reconstruct the full session: an event timeline (start/inject/query/question/answer/result/datasource with timestamps) beside a colour-coded evidence tree (rule / answer / injection / datasource / knowledgemap / synthesis per the documented source enum) showing per-condition impact and salience. Clicking a rule-inferred node jumps to the matching <relinst> in the open map — matched by relationship type, bindings, and Named Rule name, which gives internal teams a concrete reason to enforce rule naming (4.101+).
UX: Command 'Rainbird: Open Session…' → sessionID input with env picker → a two-pane webview panel: left timeline (filterable by event type), right evidence tree with expand/collapse and certainty chips. 'Reveal rule in editor' on tree nodes; 'Export CSV' mirrors the documented ?format=csv for ticket attachments; 'Replay as eval' snapshots the session's injects/answers into an .eval.json for regression pinning.
VSCode APIs: window.createWebviewPanel (CSP, asWebviewUri), postMessage/onDidReceiveMessage, window.showTextDocument + revealRange for rule jump, ExtensionContext.secrets for the three key types
Inspiration: Apex Replay Debugger (debug from logs); HCP Terraform run-log inspection; Neo4j Viz webview precedent
Risks: Interaction recording is OFF by default and per-version — sessions started before enabling are unrecoverable (UX must explain this); rule-to-source matching is heuristic when rules are unnamed; evidence requires the map's evidence key or link-share toggle.

## [Phase 2] Decision Playground Notebook (record → eval)  (surface: public-api, effort: L)
A NotebookSerializer for *.rbplay files with a NotebookController executing session cells against the live engine: %start kmID (useDraft|version), %inject [triples], %query {subject?, relationship, object?}, %answer cells for question loops, plus natural-language cells routed to POST /nl/interact (beta, Version: v1 header). Outputs render result triples with certainty chips and an evidence deep-link. The killer internal command is 'Save session as eval': an executed playground collapses into an .eval.json scenario for the harness — the record-then-regress loop solution engineers run live in customer workshops, and the fastest way to turn an exploratory RAKE/Skill-built graph into pinned regression coverage.
UX: 'Rainbird: New Playground' creates demo.rbplay with a commented skeleton. Cells execute with the standard notebook run affordance; question responses render as an interactive form (dataType-aware inputs, allowCF slider, knownAnswers chips) in a custom renderer that posts the answer back to the controller via postKernelMessage. A toolbar button converts the whole notebook or selected cells into an eval file.
VSCode APIs: notebooks contribution + NotebookSerializer, NotebookController, NotebookRenderer (vscode-notebook-renderer, postKernelMessage), NotebookCellOutputItem custom mimetype
Inspiration: MongoDB Playgrounds (3.16M installs, 4.5 stars); Microsoft REST-query notebook sample as precedent for domain notebooks
Risks: Notebook execution on vscode.dev for custom controllers is undocumented (desktop-first); /nl/interact is beta with no SLA and one-active-query-per-session semantics the UI must respect.

## [Phase 2] MCP Served-Graph Dogfooding (RAKE preview in agent mode)  (surface: undocumented-api, effort: M)
Registers graphs served via the RAKE research preview (per-graph MCP endpoints on rake.rainbird.ai; Streamable HTTP; the URL itself is the credential, so it is handled strictly as a secret) as MCP servers inside VS Code via lm.registerMcpServerDefinitionProvider returning McpHttpServerDefinition entries — URLs live only in SecretStorage and are never written to .vscode/mcp.json, settings, or logs. Internal engineers then exercise the preview's five tools (describe_graph, inject, query, answer, explain) from Copilot agent mode or the Claude Agent preview without leaving the editor — end-to-end dogfooding of the exact 'knowledge graph as MCP tool' story marketing already sells. A companion lint rule targets the preview doc's own warned footgun: instance names that match nothing are accepted silently — the harness flags eval/playground facts whose subjects match no concinst and no canAdd-enabled relationship.
UX: A 'Served Graphs' node in the Rainbird sidebar lists registered endpoints by label (never URL); 'Add served graph…' prompts for the URL into SecretStorage with a warning ('treat like a password'). Once registered, the graph's tools appear in the agent-mode tool picker; explain-tool failures surface the actionable fix ('Evidence Tree Link toggle is OFF — Studio → Publish → API Management').
VSCode APIs: contributes.mcpServerDefinitionProviders + lm.registerMcpServerDefinitionProvider, McpHttpServerDefinition, ExtensionContext.secrets, TreeDataProvider sidebar
Inspiration: Prisma/Terraform MCP server integration; VS Code MCP GA (1.102) mechanics
Risks: Research-preview endpoint with no stability guarantee; self-authenticating URLs are a leak hazard the design must actively contain (SecretStorage is not synced — a feature here); pausing/deleting the project kills the endpoint mid-session.

## [Phase 3] Evidence Regression Diff (A/B across versions and engines)  (surface: public-api, effort: L)
For any failing eval or replayed session, run the identical scenario against two targets — version N vs draft (via /start?version= vs ?useDraft=true), or two engine implementations via the x-rainbird-engine header — and structurally diff the two evidence trees: changed certainties, conditions that flipped wasMet, rules that fired in one run but not the other, weight/impact deltas. This is the concrete software behind the 'ModelOps: who changed what, when and why' pricing line: for regulated-decision customers, the question is never 'did the output change' but 'which rule and which weight changed it'. Internally it is also the engine team's release-qualification tool: run the accelerator eval corpus against the current and next engine (x-rainbird-engine) and diff every evidence tree before rollout — regression detection for the 4.107-style silent releases.
UX: On a failed eval: context action 'Compare against… → Live version / Version N / Draft / engine v2.0'. Opens a side-by-side webview: two evidence trees aligned by rule identity, differing nodes highlighted (red = certainty changed, amber = condition unmet, grey = rule absent), with a summary strip ('2 rules changed outcome: weight 100→80 on condition 3 of "APP fraud reimbursable"'). 'Open rule diff' jumps to a git diff of the responsible <relinst> when the workspace holds both versions.
VSCode APIs: window.createWebviewPanel, TestController integration (context menu on failed TestItem), vscode.diff command for the rule-level text diff
Inspiration: Miragon element-level diagram diff with color coding; Terraform plan-graph change coloring (community)
Risks: Cross-rule certainty-combination formula is unpublished, so diff explanations must stay descriptive, not causal; x-rainbird-engine values are undocumented internally-known strings; two full eval runs double query consumption.

## [Phase 3] Agent-Mode Tools + Claude Skill Distribution Channel  (surface: undocumented-api, effort: M)
Expose the extension's deterministic capabilities to in-editor agents via the languageModelTools contribution: rainbird_lint_map (client-side), rainbird_run_evals (Decisions API), rainbird_query_graph (start/inject/query), rainbird_upload_map (POST /maps, with prepareInvocation confirmation UI before any account mutation). This makes VS Code agents (Copilot agent mode, Claude Agent preview) able to do what the forum-gated Claude Skill does in 1–2 hour chat builds — but with instant local validation loops instead of upload-and-see, positioning the extension as the official successor distribution channel for the 'rainbird-graph-creation' Skill. Optionally ship the Skill's knowledge-engineering methodology as a chatSkills contribution (VS Code 1.109) so any agent in the editor inherits Rainbird's own build-test-fix doctrine. Full parity requires a decision to publish the Skill content outside the login-gated Circle forum — that piece is roadmap, the tool registration is buildable now.
UX: In Copilot agent mode, a prompt like 'build a KYC risk-rating graph from this policy PDF and make the smoke evals pass' auto-invokes lint → upload → run_evals in a visible tool loop; #rainbird_run_evals is referencable in any chat prompt. Upload always interposes a confirmation dialog naming the target account and map name.
VSCode APIs: contributes.languageModelTools + lm.registerTool, LanguageModelTool.invoke/prepareInvocation, chatSkills contribution (1.109), toolReferenceName / canBeReferencedInPrompt
Inspiration: Prisma Copilot agent-mode tools (create/apply migrations); @mongodb chat participant slash commands
Risks: Upload tool wraps the undocumented POST /maps (hence the label); chatSkills and adjacent APIs were 1.109-proposed and need a stability check at build time; distributing Skill content publicly is a product decision above the extension team.

## [Phase 3] Account Maps Sidebar with Draft Round-Trip Sync  (surface: roadmap, effort: XL)
The endgame of the text-as-source-of-truth wedge, and the biggest platform ask the extension should generate: a 'Rainbird: Maps' TreeView listing the authenticated account's knowledge maps and versions, with pull (map/version RBLang into the workspace) and push (update the SAME kmID's draft in place, not create-new), plus set-live. Today this is impossible: POST /maps is create-only and no list/pull/update endpoints exist anywhere (the OpenAPI spec states maps 'must be created via Rainbird Studio'). Building everything else first — evals, lint, upload, forensics — creates the internal demand and the ready-made client for a proper management API; this feature is the specification for that ask. Once it exists, git becomes the system of record, Studio becomes the visual client, and 'ModelOps: who changed what, when and why' is literally git blame plus the eval harness.
UX: Activity-bar container 'Rainbird' → Maps tree (map → versions → Live badge). Right-click: 'Pull draft to workspace', 'Push workspace file to draft' (with a pre-push eval gate: refuse or warn if the map's eval suite fails), 'Set version live…' with confirmation. Status bar shows dirty-vs-draft state like a git branch indicator.
VSCode APIs: viewsContainers/views + TreeDataProvider + createTreeView, authentication.getSession, SourceControl API (optional, for draft-dirty state), window.withProgress
Inspiration: Salesforce Org Browser (retrieve remote metadata) minus its CLI sprawl; Prisma cloud sidebar push-to-cloud; HCP Terraform workspace browser
Risks: Requires genuinely new platform endpoints (list maps, get RBLang by version, update draft, set live) plus conflict semantics between Studio autosave and external pushes — a real engineering and product commitment, not an extension feature; must not ship half-baked (Drools lesson).

## Journey: Solution engineer ships a new accelerator with graded evals
An SE starting the 'FCA Targeted Support' accelerator runs 'Rainbird: New Accelerator', picks the eligibility-pattern template, and gets map.rbl, evals/smoke.eval.json, and a CI workflow. She authors RBLang with schema-driven completion and rblint diagnostics catching a subject/object type mismatch as she types. She uploads the draft with the Labs POST /maps command — the toast returns a kmID and offers 'Run evals'. In the Test Explorer, 14 scenarios run against the new map via /start → /inject → /query; two fail with certainty 74 vs expected ≥80, and the TestMessage's 'View evidence' link shows an optional condition contributing 0% because a datasource fact never bound — the silent-instance-name lint she'd ignored. She fixes it, continuous test runs go green on save, commits map.rbl plus evals, and opens a PR where a reviewer reads the RBLang diff directly (no .rbird opacity) while npx @rainbird/evals gates the merge with a JSON grade report. The accelerator lands in the catalogue as a repo any Community user can clone and eval locally — the pricing-page promise, delivered by the same tooling the SE used to build it.

## Journey: Platform engineer debugs a customer regression across the changelog blackout
A support ticket arrives: an on-prem banking customer pinned at engine 4.109 gets different transaction-monitoring outcomes than the SE's demo on Community 4.118, with a sessionID attached. The engineer opens the customer's .rbird export straight in VS Code (transparent codec), then runs 'Rainbird: Open Session' — the interaction timeline shows the datasource event returning normally, but the evidence tree shows a rule condition's impact at 0. He hits 'Replay as eval' to pin the session as a scenario, then runs the Evidence Regression Diff against the current draft: the aligned trees highlight one amber condition whose expression uses isWithinRange(). The compat lint explains it — the status bar is pinned to 'target 4.109', and isWithinRange is flagged as newer than the customer's engine per the feature DB the platform team now maintains in the OSS repo (the de-facto changelog for the unpublished 4.107–4.118 window). He rewrites the condition with explicit gte/lte comparisons, the replayed eval passes against both targets, and the fix ships with a regression test that will run in CI forever.

## Journey: Labs engineer dogfoods RAKE end-to-end and hardens two undocumented APIs
A Labs engineer testing the MCP graph-serving preview builds a sanctions-screening graph with agent mode: in Copilot chat she asks for a graph from a policy doc, and the extension's LM tools loop visibly — rainbird_lint_map catches malformed conditions locally in milliseconds (instead of the Skill's upload-and-see cycle), rainbird_upload_map interposes its confirmation dialog before POSTing to /maps, and rainbird_run_evals grades the agent's own exported test suite against the live engine. She then registers the project's served-graph endpoint in the 'Served Graphs' sidebar — the self-authenticating URL goes into SecretStorage, never into mcp.json — and exercises describe_graph, query, and explain from the Claude Agent preview inside the same editor, hitting the explain error that tells her the Evidence Tree Link toggle is off in Studio's API Management. Along the way she files three issues: a /maps validation error with no line info, an MCP session that survived a project pause, and a feature-DB gap for 4.117. That feedback loop — internal engineers living on the pre-release ring — is exactly how the undocumented upload endpoint and MCP preview accumulate the contract pressure to become documented public surface, with the extension already waiting as their client.

# MISSING IDEAS
- Zero-config first-run via the public HelloWorld sandbox: docs publish a working API key and KMID for the HelloWorld map on api.rainbird.ai (api.md). A walkthrough step and bundled demo playground/eval suite could run end-to-end with zero account, zero config — the strongest possible zero-config activation story for all three audiences, and the internal demo the sales team can run in any meeting. The design's onboarding currently assumes an authenticated account.
- Docs-surface integration: docs.rainbird.ai is GitBook with an llms.txt index, .md raw mirror of every page, and a ?ask=<question> NL query API (api.md, gap-4 — 'agent-optimized docs'). Unexploited: hover cards and diagnostics could deep-link the exact .md reference page per element/function; an lm tool (rainbird_docs) or chat participant could answer authoring questions via ?ask= with zero platform work; the OSS language server could vendor the .md corpus for offline hovers.
- Rule coverage painting from eval runs: the VS Code Test Coverage API is finalized (1.88, vscode.md) and OPA's Toggle Coverage is a ranked comps pattern. Each eval result's recursive evidence tree identifies exactly which <relinst> rules fired — a Coverage-kind run profile could paint covered/uncovered rules in-editor and report never-exercised rules across the accelerator corpus. This is the natural upgrade from 'graded evals' to 'graded evals with knowledge-map coverage', and no comps competitor of Rainbird has it.
- contextid/scope support: /start/{kmID}?contextid={CONTEXT_ID} shares facts across sessions for scope-enabled concepts/relationships (legacy-documented, still live — Go SDK exposes contextID, the Studio validator accepts scope='context', and /analysis/session?filter=facts returns a distinct 'context' bucket). Entirely absent from the design: eval scenarios spanning multiple sessions, lint/completion for the scope attribute, and forensics rendering of the context-facts partition.
- Question-group handling: rel@group and the extraQuestions[] array in questionResponse (api.md) mean real maps return grouped questions in one turn. The eval runner's scripted answers and the notebook's answer forms must consume extraQuestions or they stall on group-using maps; a lint for inconsistent group names across rels is also cheap. Nowhere addressed in the design.
- Reference-client hardening of documented discrepancies: the JS SDK sends 'cf' where REST docs say 'certainty', and the Go SDK's EnvEnterprise base URL (api-enterprise.rainbird.ai) conflicts with the documented enterprise-api.rainbird.ai (both api.md). The shared runner/client core will become Rainbird's de-facto reference client — it should test both aliases in the internal ring, normalize, and file the resulting contract bugs; cheap wins that directly serve the 'harden undocumented surfaces into contracts' thesis.
- POST /{sessionID}/undo in the playground: the documented undo endpoint (rolls back the last answer array, repeatable) is used nowhere in the design — a %undo cell in the notebook is a trivial addition that makes live customer-workshop demos genuinely interactive and exercises an endpoint no current Rainbird tooling surfaces.
- Studio evidence deep-link as the cheap evidence UX: the documented [STUDIO_HOST]/evidence?id={factID}&api={API_HOST}&sid={sessionID} link pattern (api.md) gives the eval harness and playground a working 'View evidence' affordance on day one — before the Phase 2 forensics webview exists — closing the MVP gap identified in the harness verdict at near-zero cost.
