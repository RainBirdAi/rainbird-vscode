# Design: architecture

## Overview
Design thesis: Rainbird's own developer page promises "export, diff, review in a pull request, and regression test in your CI process" — and today there is zero tooling behind that sentence. The extension's architecture makes plain-text RBLang in git the canonical artifact and builds every layer outward from it: (1) an offline, license-clean language core; (2) an opt-in platform layer over the documented Decisions/Evidence API; (3) an honestly-labelled frontier layer over the undocumented POST /maps upload and the RAKE MCP preview, which doubles as the concrete ask-list for the platform team.

Five architectural commitments drive everything. First, RBLang gets its own language id ('rblang'), not an XML injection — an owned id is the anchor for LSP document selectors, CodeLens, tests and debugging, and avoids fighting Red Hat XML over a namespace whose schema URL (rbl.io) Rainbird no longer even controls. Second, the language server is a from-scratch TypeScript reimplementation using the extracted Studio validator table (module 1579), rblint checks, and the 51-function expression catalog strictly as a specification — never copied code — bundled in-process (Prisma's WASM/performance lesson, Terraform's bundled-LS lesson) and web-worker-capable from day one. Third, .rbl text files are the source of truth; .rbird (gzipped JSON) round-trips losslessly via import/export commands with a layout sidecar, so Studio and git coexist instead of competing. Fourth, everything platform-connected is offline-degradable and zero-config: no mandatory config file (GraphQL/Apollo's 3-star mistake), no subprocess sprawl (Salesforce's 2.5-star mistake), one extension, not a pack. Fifth, the "debugger" story is honest about server-side constraints: there is no local engine, so the MVP debugger is the evidence-tree post-mortem (Rainbird's actual differentiator), the P2 debugger is a DAP adapter that steps the real question loop (with POST /undo as genuine step-back), and true rule breakpoints are explicitly roadmap, blocked on an engine trace API.

The comps research sets the quality bar: Regal's eval CodeLens with a convention-based facts file, Prisma-grade LSP polish, Neo4j's connected-platform intelligence, Miragon's text-first graph editing. The incumbent is a 455-install snippets extension abandoned in 2019; the field is open, and Rainbird's richest editor assets already exist as extractable specs.

## Personas
- Customer knowledge author — a policy/domain expert at a Rainbird customer (e.g. a BDO tax analyst or DAC Beachcroft fraud lead) who normally works in Studio but needs governance: PR review, diffable versions, regression safety before setting a version live
- Internal Rainbird engineer — builds accelerators, library templates and customer maps; needs engine-parity linting (Studio's own legacy code panel autocomplete lags the engine by 8+ functions), fast RBLang editing, and repeatable eval/test runs
- Third-party integrator developer — builds decision services and agents against the Decisions API, SDKs and MCP; needs API-loop tooling, evidence-tree debugging, CI regression tests, and AI-agent integration without Studio in the loop

## [MVP] Own 'rblang' language id with dual TextMate grammar (XML host + embedded expression language)  (surface: client-only, effort: S)
Contribute language id 'rblang' bound to .rbl (canonical) plus automatic language-mode switching for .xml files whose root is <rbl:kb ...> (detected on open, switched via languages.setTextDocumentLanguage — VS Code's firstLine detection can't distinguish RBLang from generic XML). Grammar strategy: a self-contained source.rblang grammar implementing XML-shape rules specialized to the real element/attribute vocabulary (concept, rel, relinst, concinst, condition, compound, import, datasource, action, input, headers, header, meta, firstForm, secondFormObject, secondFormSubject — the exact set in Studio's validator), plus a second grammar source.rblang-expression injected into the string content of expression="..." and value="..." attributes, scoping the 51 engine functions, natural-language operator aliases ('is greater than or equal to', gt, gte…), %UPPER_SNAKE variables, %S/%O reserved variables, and single-quoted string literals. meta.embedded.* scopes + the embeddedLanguages map give correct bracket matching and commenting inside expressions. Alternatives considered: (a) pure injection grammar into text.xml — rejected: no owned document selector for LSP/CodeLens/tests, and Red Hat XML extension would fight over validation of a namespace whose schema URL (rbl.io) is domain-squatted and serves a shirt shop; (b) adopting the incumbent tom-sherman extension — rejected: it contributes no language and no grammar at all, only 11 XML snippets, abandoned since 2019.
UX: A user opens claims-triage.rbl: elements and attributes are colored, expression strings light up like a real language (functions, operators, variables distinct), -- comments and alt text render as comment/string scopes. Opening a Studio-exported .xml flips to 'RBLang' in the status-bar language picker automatically. Zero configuration, zero prompts.
VSCode APIs: contributes.languages, contributes.grammars (embeddedLanguages, injectTo), languages.setTextDocumentLanguage, contributes.snippets
Inspiration: Cedar's convention-based file detection; Prisma's owned-language polish; coffeebird's grammar as prior art
Risks: Expression tokenization inside XML attribute strings is regex-fragile for multi-line attributes; mitigated because semantic tokens from the LS override TextMate for the hard cases.

## [MVP] From-scratch TypeScript language server, Studio validator + rblint treated as a reimplementation spec  (surface: client-only, effort: L)
A bespoke LS built on vscode-languageserver-node (client: vscode-languageclient v10), bundled in the extension with dual node + web-worker builds. Parsing: an error-tolerant streaming XML parser (saxes-class, position-tracking) producing a lossy-tolerant AST per document, incrementally reparsed. Diagnostics reimplement three extracted-but-proprietary Rainbird artifacts as specification (license note: extracted Studio assets are treated as spec to rebuild, never code to copy — flagged for legal review): (1) the structural validator table from Studio bundle module 1579 (element nesting, required/optional attrs, enum validators like askable ∈ true|false|all|none|secondFormSubject|secondFormObject, canAdd sets, concept behaviour mutually-exclusive|mutex|mx, min/max children, text-element rules — including correctly enforcing condition@behaviour, which is dead code in Studio due to a nesting bug we don't replicate); (2) rblint semantic checks (duplicate concinsts/facts, unknown concept/relationship types, subject/object type agreement, only-string-subjects, date/number/truth literal validity, datasource %S input typing); (3) an expression parser implementing the documented left-to-right (non-PEMDAS) evaluation, the full 51-function catalog with arities, single-quoted literals, no-null-test rule, and variable-flow analysis (%VARs bound by relationship conditions vs consumed by expressions, appears-≥2-times lint, custom variables illegal in rule headers). Adds map-level lints Studio lacks: condition weight sum > 0, minimumRuleCertainty ≤ cf, forbidden name chars " ' \ < >, mutually-exclusive concepts requiring exactly 2 instances, orphan concepts. Emits Studio's exact error phrasing ('X element has missing attribute: Y') so authors see identical messages in both tools. Alternatives considered: (a) Red Hat XML LS + custom XSD — rejected: no XSD exists anywhere (even internally the cheerio table appears canonical) and cross-element semantic checks (type agreement, variable flow) are inexpressible in XSD; (b) reusing Studio's JS directly — rejected on license; (c) tree-sitter grammar — deferred: nice for future editors but VS Code LSP doesn't need it and nothing exists to reuse.
UX: Red squiggles as you type with Studio-identical wording plus richer engine-truth lints; Problems panel groups by map; a typo in a relationship name inside condition rel="..." is flagged with a did-you-mean. The LS also validates that expressions only use functions the live engine actually supports — beating Studio's own legacy code panel, whose autocomplete lags the engine by 8+ functions.
VSCode APIs: vscode-languageclient v10 (LanguageClient, documentSelector), vscode-languageserver-node (browser + node builds), DiagnosticSeverity/CodeDescription
Inspiration: Regal (most complete rules-DSL LSP found); Prisma's in-process performance discipline; Drools as the cautionary tale of a half-committed LSP
Risks: Engine drift: changelog publication stopped at v4.106 while the engine is at 4.118, so the spec baseline must be re-verified against live behavior; grammar corpus for regression testing is small (real .rbird maps at /tmp/rblang/). Legal sign-off needed on the reimplementation-not-copy stance.

## [MVP] Workspace index: context-aware completion, navigation, rename, semantic tokens  (surface: client-only, effort: L)
The LS maintains a cross-file symbol index (concepts, rels, instances, rules, facts, imports) over the workspace. Completion architecture ports the *design* of Studio's contextAwareCompleter but AST-based instead of regex-line-scanning: infer the enclosing element context (top-level/relationship/rule/concept/datasource/instance/header/meta/compound), offer element snippets for that context, filter attribute completions to those not already present, and — the layer Studio doesn't have across files — complete VALUES: concept names inside rel@subject/object, relationship names inside condition@rel, relinst@type and action@map, typed instance names inside fact subject/object, bound %VARIABLES within the current rule, and expression functions/operator aliases (full 51-function set with signature help) inside expression="...". Snippet catalog achieves parity with Studio's ace/snippets/rblang list (rule/fact/compound/datasource GET+POST+CDATA/markdown meta/import). Navigation: document symbols (outline groups Concepts/Relationships/Instances/Facts/Rules using rule name attr from Named Rules v4.101), go-to-definition and find-references on any name, F2 rename updating every reference including inside expressions and {{%VAR.dot-traversal}} alt text. Semantic tokens do what TextMate cannot: classify bare names in attribute values as concept/relationship/instance/variable references (token types: type, property, enumMember, variable, function). Alternatives considered: request-forwarding to built-in XML providers — rejected: cannot produce diagnostics and knows nothing about RBLang semantics.
UX: Ctrl+Space inside a rule offers exactly the three condition forms plus aggregate-function skeletons; typing rel=" lists only relationships whose shape fits; hovering 'sumObjects' shows signature + docs link; F2 on a concept renames it in 40 places across 3 imported map files; the outline shows named rules as navigable items.
VSCode APIs: LSP completion/definition/references/rename/documentSymbol, DocumentSemanticTokensProvider via LSP semanticTokens, SignatureHelp, contributes.semanticTokenScopes
Inspiration: Studio's contextAwareCompleter (as spec); Prisma's context-aware completion with back-relation insertion; Neo4j label-aware completions
Risks: Rename inside free-text alt/evidence strings requires conservative matching to avoid corrupting prose; mitigate with preview-before-apply (WorkspaceEdit preview).

## [MVP] .rbl canonical text format with lossless .rbird import/export (layout sidecar)  (surface: client-only, effort: M)
Decision: git stores plain text; .rbird stays the Studio interchange format. .rbird is verified gzip-JSON ({format:'rbird', studioData:{layout…}, unicronData:{rblang:[lines]…}}), so the extension ships pako-based (web-safe, no native deps) commands: 'Rainbird: Import .rbird…' explodes it into <name>.rbl (the unicronData.rblang lines), README.md (the readme), and <name>.layout.json (studioData graph coordinates); 'Rainbird: Export .rbird…' re-assembles all three so a Studio re-import preserves node positions — the detail that makes round-tripping actually pleasant for Studio-first authors. Dropping/opening a .rbird directly shows a read-only summary page (concept/rel/rule counts, readme) with a 'Convert to project' button via a binary CustomEditorProvider (P2 polish; MVP ships the commands). Alternatives considered: (a) FileSystemProvider mounting .rbird as a virtual workspace — rejected: the strategic wedge is real text files in git for diff/PR; virtual files defeat it; (b) making .rbird the editable format via CustomEditorProvider — rejected: same reason, plus undo/dirty semantics on a gzip blob are hostile; (c) inventing a new extension like .rblang — .rbl chosen as short, unclaimed, and already colloquial.
UX: Author exports from Studio, drags kyc.rbird into VS Code, clicks Import: a folder appears with kyc.rbl + README.md + kyc.layout.json; edits and git history happen in text; before re-importing to Studio she runs Export .rbird and gets a file Studio accepts with layout intact.
VSCode APIs: commands.registerCommand, workspace.fs, CustomEditorProvider (readonly, P2), contributes.customEditors priority:option
Inspiration: Miragon/bpmn-js 'text file stays the source of truth'; rbdat (Rainbird's own gunzip pretty-printer) proving the format
Risks: .rbird internal version field (1.1) could change silently given the changelog blackout; importer validates format/version and fails loud with a 'report this' link.

## [MVP] Zero-config 'Rainbird project' folder convention that round-trips git, Studio and CI  (surface: client-only, effort: S)
Convention over configuration: a Rainbird project is any folder containing a .rbl map; optional conventional siblings are tests/*.rbtest.json (Studio Automated Tests JSON export format, verbatim), facts/*.facts.json (convention-based inject payloads for the query CodeLens, stolen from Regal's input.json discovery: walk up from the file to workspace root), evals/ (accelerator-style graded evals), README.md and <map>.layout.json. A single OPTIONAL dotfile .rainbird.json ({environment, kmId, version|useDraft}) binds the folder to a platform map for push/query/test defaults — but every language feature, and even querying (via prompt-and-remember), works without it; it is never required to activate anything. The extension contributes a workspace TreeView 'Rainbird' listing detected projects with their map/tests/facts and connection binding state. Alternatives considered: (a) mandatory manifest a la graphql-config/apollo.config.json — explicitly rejected, it is the documented #1 friction driving those extensions to 3 stars; (b) sfdx-style scaffolding CLI — unnecessary, a folder + one file is the whole convention.
UX: git clone of a colleague's repo just works: maps get diagnostics instantly, Test Explorer populates from tests/, the Rainbird view shows 'kyc-map — bound to Community (draft)'. 'Rainbird: New project' scaffolds map.rbl + tests/ + README from a template picker (hello-world, accelerator skeletons).
VSCode APIs: workspace.findFiles/FileSystemWatcher, TreeDataProvider + window.createTreeView, viewsWelcome, workspace.workspaceFolders
Inspiration: Regal's convention-based input.json; Cedar's file-convention autodetection; anti-pattern: GraphQL/Apollo mandatory config
Risks: The Automated Tests JSON schema is observed-from-exports rather than formally documented; schema published by platform team is a P2 ask.

## [MVP] AuthenticationProvider + per-environment SecretStorage and typed API client (offline-first)  (surface: public-api, effort: M)
Platform connectivity is one layer: an AuthenticationProvider (id 'rainbird') whose sessions represent environment+key pairs. createSession flow: pick environment (Community api.rainbird.ai / Enterprise enterprise-api.rainbird.ai / custom private URL like {client}-api.rainbird.ai or self-hosted) → paste X-API-Key (with deep link to the Account/Publish page where keys live) → key stored in ExtensionContext.secrets namespaced per environment; sessions appear in the Accounts menu; multiple environments concurrently (dev community + prod enterprise). Separate optional secrets per map for x-evidence-key and x-interaction-key. The API client is a small typed layer generated from the published OpenAPI 3.1 spec (api.rainbird.ai/docs/openapi.yaml v1.2.0) covering /start, /{sid}/inject|query|response|undo, /analysis/evidence|interactions|session, /nl/interact|/nl/explain (Version:v1 header), GET /version — fetch-based (web-compatible), with backoff and honest 401/403/404 error surfacing. Offline-first rule: the extension NEVER blocks or prompts for auth until the user invokes a platform action; all language tooling is fully functional disconnected. Status bar item shows environment + live engine version (unauthenticated GET /version) and doubles as the connection switcher. Alternatives considered: (a) settings.json for keys — rejected, keys land in dotfiles/git; (b) OAuth — Rainbird has no OAuth surface; API-key AuthenticationProvider is the honest fit and still yields Accounts-menu UX; (c) per-request key prompts — hostile.
UX: Click 'Rainbird: Sign in' from the status bar or Accounts menu, pick Community, paste key, done — status bar shows 'Rainbird 4.118 · Community'. A 401 on any call offers 'Update API key' inline. Nothing about editing ever asks for an account.
VSCode APIs: authentication.registerAuthenticationProvider + contributes.authentication, ExtensionContext.secrets (SecretStorage), window.createStatusBarItem, env.openExternal
Inspiration: Neo4j multi-instance connection management; HCP Terraform login UX; Prisma Console sign-in sidebar
Risks: No whoami endpoint exists to validate a key cheaply — validation is lazy (first real call); Go SDK's conflicting enterprise URL (api-enterprise vs enterprise-api) means the env picker must let users override the base URL.

## [MVP] 'Run Query' CodeLens with interactive question loop and convention facts file  (surface: public-api, effort: M)
The Regal-eval pattern mapped to Rainbird's shape: every <rel> gets a 'Query' CodeLens (object/subject/certainty query picker) and every rule <relinst> gets 'Test this rule' (queries the rule's type). Execution: resolve the map binding (.rainbird.json kmId, or prompt-and-remember), GET /start/{kmID}?useDraft=true (draft-first workflow; version pinning available), auto-inject the nearest *.facts.json (≤250 facts/batch as documented), POST /{sid}/query {relationship, subject?, object?}, then drive the documented question/result loop: First Form questions render as yes/no QuickPick, Second Form as QuickPick over question.concepts[] candidates or typed InputBox for number/date/truth (validated against dataType), honoring allowUnknown (skip button), allowCF (optional certainty 1–100 input), and extraQuestions grouping. Result renders inline as an editor decoration on the rel line — subject/object + certainty% — with actions: 'Show evidence tree', 'Save as test', 'Undo last answer' (POST /undo). Alternatives considered: (a) a separate 'query panel' webview first — rejected as MVP: CodeLens-in-the-file is the proven highest-value affordance (Regal, GraphQL Inline Execution) and needs no new UI surface; (b) local engine evaluation — impossible, no local engine exists; the loop is honest remote execution against draft.
UX: Author places cursor on <rel name="requires enhanced due diligence"...>, clicks 'Query ▶', picks a subject instance from completions, answers three questions via QuickPicks, and sees 'true · 85%' appear inline with an evidence link — without leaving the file. 'Save as test' snapshots the exact Q&A script into tests/ as a Studio-format JSON test.
VSCode APIs: languages.registerCodeLensProvider, window.createQuickPick/showInputBox, TextEditorDecorationType (inline results), progress API (withProgress)
Inspiration: Regal's Evaluate code lens + input.json convention; GraphQL Inline Operation Execution variable prompts
Risks: Requires the map to already exist on the platform (no public upload API) — the draft being queried is Studio's draft, not necessarily the local file; the UI labels results 'remote draft' until Push (P2) closes the gap. 24h question expiry and undocumented session TTLs need defensive re-start handling.

## [MVP] Evidence-tree post-mortem viewer (the realistic 'debugger', part 1)  (surface: public-api, effort: L)
Rainbird's differentiator is that every decision yields an evidence tree — so the extension's flagship debugging surface is a webview that reconstructs it: after any query/test run, recursively GET /analysis/evidence/{factID}/{sessionID} (x-evidence-key aware) following condition factIDs (the documented fullEvidence pattern), and render an expandable tree: nodes color-coded by source enum (knowledgemap|rule|answer|injection|datasource|synthesis) matching Studio's palette, per-fact certainty, rule nodes showing bindings (%S/%O/%COUNTRY), per-condition impact and salience bars (a mini Salience Chart), expression conditions with text/value/wasMet. The killer interaction: every rule node deep-links back into the text — resolved via Named Rule name when present, else relinst type + condition fingerprint — so 'why did this decide X?' becomes click-to-the-line. Toolbar: open in Studio (documented deep-link [STUDIO_HOST]/evidence?id=&api=&sid=), copy factID, 'Explain in English' via POST /nl/explain (beta). Built as a WebviewPanel with vscode-elements (the official Webview UI Toolkit is deprecated), CSP-locked, state via getState/setState. Alternatives considered: (a) TreeView instead of webview — rejected: no salience bars, no color semantics, no custom layout; (b) waiting for DAP to be the debug story — rejected: post-mortem evidence is buildable today on documented API and is what users actually need first.
UX: After a query returns 62%, the author clicks 'Show evidence': a side panel shows the goal fact at top, red 'answer' nodes and dark-green 'datasource' nodes beneath, an orange hard-coded fact she forgot about, and a salience bar showing one optional condition contributed 0%. Clicking the rule node jumps the editor to line 214.
VSCode APIs: window.createWebviewPanel, Webview postMessage/onDidReceiveMessage + asWebviewUri + CSP, TextEditor.revealRange (jump-to-rule), workspace.onDidChangeTextDocument (stale-marker)
Inspiration: Apex Replay Debugger (debug from logs, not live process); Studio's own evidence tree UI as visual spec
Risks: Evidence requires the map's evidence key or link-share toggle — first-run UX must explain the Studio-side toggle; recursive fetches on deep trees need batching/caching (query depth limit is 2,000,000 in theory).

## [MVP] Test Explorer for Automated-Tests JSON + shared-core CI runner  (surface: public-api, effort: L)
Delivers the literal marketing promise ('regression test in CI', 'graded evals in your CI') that has no tooling today. A TestController maps tests/*.rbtest.json (Studio's Automated Tests export format — recorded query + scripted answers + expected results) to hierarchical TestItems (file → test → assertion). Run profile executes each test against the platform: /start (useDraft or pinned version from .rainbird.json), inject for results-only tests, or drive the query/response loop feeding scripted answers; compare expected subject/object/certainty with TestRun.passed/failed and TestMessage expected/actual diffs, plus errored for engine/API failures. supportsContinuousRun re-runs affected tests on save (matching tests by relationship touched). Coverage profile (P3 stretch): after a run, mark which rules appear in any result's evidence tree — FileCoverage painting fired/unfired rule elements, the OPA coverage-toggle analog and a genuinely novel 'rule coverage' metric for the category. The test execution core is an extension-independent npm package (same analyzer the LS uses) shipped with a tiny CLI (rainbird-test run --env --km) and a documented GitHub Action recipe, so CI runs bit-identical logic to the editor. Alternatives considered: (a) inventing our own test format — rejected: Studio import/export of the JSON is the round-trip contract; we adopt it verbatim and add nothing; (b) notebook-based tests (MongoDB playground style) — deferred to P3 as an authoring nicety, not the system of record.
UX: Test beaker icon shows 'kyc-map (14 tests)'; Run All executes against the draft in ~seconds each; a failure shows 'expected: high risk · 80% / actual: high risk · 65%' with a diff and a 'Show evidence' link on the failing result; the same suite runs in the repo's CI via the Action.
VSCode APIs: tests.createTestController, TestRunProfile (Run/Coverage, supportsContinuousRun), TestMessage.diff, FileCoverage/loadDetailedCoverage (P3)
Inspiration: OPA workspace tests + coverage toggle; Kogito SceSim scenario testing; Apex Test sidebar
Risks: Test JSON schema is inferred from exports (undocumented) — needs a corpus and a platform-team schema publication (P2 ask). Draft-vs-version semantics: CI should pin versions; the runner defaults CI to a pinned version and warns on useDraft.

## [MVP] MCP server registration for served graphs (mcpServerDefinitionProvider)  (surface: undocumented-api, effort: S)
First AI feature to ship because the platform side already exists: Rainbird's RAKE research preview serves any published graph as a Streamable-HTTP MCP endpoint exposing describe_graph/inject/query/answer/explain tools, where the URL itself is the credential. The extension contributes an McpServerDefinitionProvider: command 'Rainbird: Register served graph…' prompts for the endpoint URL, stores it in SecretStorage (it is a self-authenticating secret — never in settings.json, never in git, masked in UI), and publishes an McpHttpServerDefinition so Copilot agent mode (and any MCP-aware flow in VS Code ≥1.102 GA) can immediately call the graph's tools. onDidChangeMcpServerDefinitions fires on add/remove/pause. Zero server code to write or host. Alternatives considered: (a) building our own MCP server wrapping the REST API — redundant with the platform's preview and would duplicate auth handling; revisit only if the preview lags; (b) .vscode/mcp.json instructions in docs — rejected as primary path: it would push secret URLs into workspace files; the provider + SecretStorage is the safe channel.
UX: Developer pastes the served-graph URL from the RAKE dashboard into the command; a 'rainbird-kyc' MCP server appears in the chat tools picker; in agent mode they type 'check if ACME Ltd requires enhanced due diligence and explain why' and the agent chains query → answer → explain against the live graph.
VSCode APIs: contributes.mcpServerDefinitionProviders, lm.registerMcpServerDefinitionProvider, McpHttpServerDefinition, SecretStorage
Inspiration: Prisma/Terraform MCP integration; VS Code MCP GA (1.102)
Risks: Research-preview surface: URLs can be paused/deleted from the dashboard and semantics may change without notice (changelog is dark since 4.106); feature is flagged 'preview' in UI. Platform ask: publish MCP docs and a stable URL/auth story.

## [MVP] Single-extension packaging: bundled LS, esbuild, pre-release channel, Open VSX  (surface: client-only, effort: M)
Packaging decisions: ONE extension under a Rainbird-verified publisher (supersedes the abandoned personal-publisher incumbent; domain verification signals officialness) — explicitly not an extension pack (Salesforce's 18-extension sprawl and subprocess farms drive its 2.5 stars). The language server is bundled and spawned via vscode-languageclient IPC (Terraform's bundled-LS zero-install lesson) with an in-process fallback; no separate downloads, no version-matching churn. esbuild single-file bundling for extension host, LS (node + browser targets), and webview assets; pure-TS dependency policy (pako for gzip, no native modules) keeps every platform target and the future web build on one artifact. Release engineering: pre-release channel via vsce --pre-release with the even/odd minor convention for fast iteration during the platform's undocumented-API stabilization; publish to Open VSX from day one (Cursor/VSCodium/code-server reach — search confirms zero rainbird/rblang presence there, free greenfield); no SVG icons per marketplace rules; CI matrix runs @vscode/test-electron plus @vscode/test-web smoke. Alternatives considered: separate 'language' + 'platform' extensions — rejected: the platform layer is thin and optional at runtime, and two SKUs doubles support surface for zero user benefit.
UX: One install from Marketplace or Open VSX; first activation is instant (activation events scoped to onLanguage:rblang, workspaceContains:**/*.rbl, and the auth/view/command events — never '*'); the walkthrough auto-opens. Pre-release users get weekly builds.
VSCode APIs: @vscode/vsce (pre-release publishing), esbuild bundling, activation events (onLanguage, workspaceContains), @vscode/test-web
Inspiration: Terraform bundled LS; anti-patterns: Salesforce pack sprawl, Drools fragmentation
Risks: Publisher namespace/marketplace account setup needs Rainbird org decisions (Entra ID federation, since global PATs retire Dec 2026); coordinate with Tom Sherman regarding the incumbent's deprecation notice.

## [MVP] Onboarding walkthrough: first decision in 60 seconds via the public sandbox  (surface: public-api, effort: S)
A contributes.walkthroughs checklist that gets any persona to a live decision without an account: Step 1 opens a bundled hello-world.rbl (Person-speaks-Language, mirroring the docs quickstart); Step 2 runs the Query CodeLens against the docs-published HelloWorld sandbox (Rainbird publishes a sandbox API key and KM ID in its public docs, so zero credential entry is needed for the first touch); Step 3 opens the evidence tree; Step 4 connects the user's own account (AuthenticationProvider); Step 5 imports a .rbird from Studio or downloads an accelerator. completionEvents (onCommand, onView) check steps off automatically. Alternatives considered: README-only onboarding — rejected; walkthroughs are the sanctioned pattern and the comps show onboarding friction is the difference between 5-star and 3-star DSL extensions.
UX: On install the Welcome page shows 'Get started with Rainbird' with five checkable steps and theme-aware SVGs; a brand-new integrator reaches a certainty-scored answer with an evidence tree in under a minute, before ever creating an account.
VSCode APIs: contributes.walkthroughs (completionEvents), viewsWelcome, commands
Inspiration: VS Code walkthrough UX guidance; MongoDB playground first-run
Risks: Sandbox key rotation would break step 2; fallback path prompts sign-in.

## [Phase 2] Knowledge-map graph preview webview (read-only, text remains source of truth)  (surface: client-only, effort: L)
A side-by-side WebviewPanel rendering the LS's AST as an interactive graph: concepts as typed nodes, rels as directed edges, badges for rule/fact counts, filters (askable-only, datasource-backed, by group), and minimap. Layout: reuse Studio coordinates from the .layout.json sidecar when present (visual parity with what the author saw in Studio), else automatic layout via elkjs/fcose. Library decision: cytoscape.js (MIT, canvas, mature, no watermark obligations) — chosen over bpmn-js (bpmn.io license requires watermark and its BPMN meta-model is wrong for knowledge graphs), raw d3 (too low-level for hit-testing/selection at map scale), and Neo4j NVL (licensing unclear per comps research). Sync architecture: preview-panel pattern, NOT CustomTextEditorProvider — document→graph updates flow from onDidChangeTextDocument through the LS's incremental AST (debounced), graph→document interaction is limited to selection (click node/edge → revealRange of its definition; cursor moves highlight the graph). This dodges the undo-granularity and echo-loop hazards the research flags for CustomTextEditorProvider while proving the rendering pipeline that P3 editing will reuse. Alternatives considered: full graphical editing now — rejected: Miragon and draw.io prove text-first preview earns trust before write-back; editing is a separate P3 decision.
UX: Ctrl+Shift+E-style toggle 'Open Graph Preview to the Side'; the graph re-lays-out live as the author types a new <rel>; clicking the 'requires enhanced due diligence' edge scrolls the editor to it; a PR reviewer opens the preview on a diff to see what the change means topologically. Export as SVG/PNG for docs.
VSCode APIs: window.createWebviewPanel (ViewColumn.Beside), workspace.onDidChangeTextDocument (debounced), TextEditor.revealRange + onDidChangeTextEditorSelection, webview getState/setState
Inspiration: Miragon BPMN text-as-source-of-truth + diagram/XML toggle; Prisma ERD visualization; Neo4j Viz webviews; hediet/vscode-drawio sync architecture

# MISSING IDEAS
- RBLang document formatter (LSP documentFormattingProvider, format-on-save): comps rank formatting as a core 5-star-vs-3-star differentiator (Prisma format-on-save, Cedar formatting), Studio's serializer conventions are known (two-space indent, self-closing emission verified in gap-3), and the docs prescribe a recommended element order (concepts → rels → instances → facts → rules). A canonical formatter minimizing diff noise is load-bearing for the 'review in a pull request' wedge, yet no feature in the design mentions formatting at all — ironically the incumbent extension's marketplace category was 'Formatters'.
- Facts/tests payload linting against the map index: mcp-preview.md explicitly warns that unrecognized instance names in injected facts are 'accepted silently and attach to nothing' and suggests an extension linter could catch it. The LS already indexes concinsts/rels — validate *.facts.json, tests/*.rbtest.json and LM-tool inject payloads for unknown subjects/objects/relationships, wrong dataType literals (ISO/epoch dates, 15-digit number precision, ≤2000-char strings, forbidden " ' \ < > chars), and >250-fact batches. Cheap, client-only, and it hardens the Query CodeLens, Test Explorer, DAP and MCP flows simultaneously.
- Production-session import: 'Open session…' command that takes a sessionID, pulls GET /analysis/interactions/{sid}?format=json (x-interaction-key) and GET /analysis/session?filter=facts, reconstructs the query + answer script, renders the evidence tree, and offers 'Save as regression test' into tests/. This turns real production incidents into CI test cases — the true Apex-Replay-Debugger analog — where the design only replays interactions for sessions the extension itself started. Also surfaces the documented CSV export for audit teams (ModelOps story).
- NL quick-query via POST /nl/interact: the design uses /nl/explain but never /nl/interact (X-API-Key + Version:v1, responseType question|result|error, extracted query, invalid/unmatched fact feedback). A 'Query in plain English' command/panel gives integrators a Copilot-free NL testing surface mirroring Studio's NL test agent, and its unmatched/invalid-facts response is itself a lint signal on question wording and instance coverage.
- Docs ?ask= grounded help with zero Copilot dependency: docs.rainbird.ai supports a ?ask=<question> NL query API on any page URL (confirmed). A 'Rainbird: Ask the docs' command (QuickInput → cited GitBook answer in a webview/hover) serves the majority of users who lack Copilot entitlement, and doubles as the backend for the P3 participant's /docs command instead of raw .md retrieval + lm.selectChatModels synthesis.
- Engine-drift regression harness via x-rainbird-engine: the documented header selects experimental/alternate engine implementations per session. Add an 'engine variant' option to the test runner/CI CLI to run the same suite against default and experimental engines and diff certainties — directly mitigating the changelog-blackout risk (dark since 4.106 while the engine is at 4.118) that the LS's engine-parity promise depends on, and giving Rainbird's own engineers a pre-release canary they currently lack.
- contextid/scope support: /start?contextid= shares facts across sessions for scope='context' concepts/relationships (documented legacy, still in the Go SDK and the /analysis/session 'context' facts bucket, and rel scope='context' is in the module-1579 validator). Knowledge authors hold tabular reference data (sanctions lists, product matrices); a paste/import-CSV → <concinst>/<relinst> generator (and → facts.json for inject payloads) is an S-effort, client-only feature with proven demand from the 455-install prior art.
