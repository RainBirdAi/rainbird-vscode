# Design: integrators

## Overview
Rainbird's own developer page promises integrators "export, diff, review in a pull request, and regression test in your CI process" and "expose any knowledge graph as an MCP tool" — but the shipped surface is an OpenAPI YAML you're told to import into Postman, two SDKs (JS and Go), and zero tooling. For third-party integrator developers — engineers who consume decisions but may never write a line of RBLang — the VSCode extension should be the missing developer console for the Rainbird Decisions API. The design thesis has four strands. (1) Session-loop ergonomics: Rainbird's core integration challenge is unusual — a decision is a stateful conversation (start, inject up to 250 facts, query a goal, answer follow-up questions or undo, loop to a result), and every result carries a factID pointing into an evidence tree. The extension makes that loop tangible: an interactive Session Runner with a raw wire log, convention-based decision-request files with a Regal-style "Run decision" code lens, and one-click copy-as-code into @rainbird/sdk, Go, or curl. (2) Text/git as source of truth: sessions, tests, and eval suites are plain JSON files that diff cleanly in PRs and run headlessly in CI via a bundled runner — making the marketing promise real. (3) Evidence as a first-class debugging artifact: integrators get results their app cannot explain; the Evidence Tree Inspector recursively walks /analysis/evidence factIDs into a color-coded tree with impact/salience, /nl/explain narratives, and audit-ready exports. (4) Agent-stack readiness: one command registers a served graph's MCP endpoint (a URL that is itself a credential) into VS Code, Claude Code, or Claude Desktop with SecretStorage hygiene, and Copilot LM tools let agent mode run decisions without any MCP preview dependency. Everything MVP-tier runs against today's documented API with zero config files (the GraphQL/Apollo anti-pattern), keys in SecretStorage (never the repo), and a first-run walkthrough that executes a real decision against the docs-published HelloWorld sandbox before the user even has an account. Undocumented surfaces (rake.rainbird.ai MCP preview, POST /maps) are labeled honestly and isolated so their churn cannot break the core.

## Personas
- Platform engineer at a customer or SI embedding Rainbird decisions into a backend service via the REST Decisions API or @rainbird/sdk / Go SDK
- Agent-stack AI engineer wiring served Rainbird graphs into Claude Code, Claude Desktop, Copilot agent mode, or other MCP clients
- Frontend developer building a question-loop UX with @rainbird/sdk-react or the sdk-react-material KitchenSink component
- QA / DevOps engineer who owns decision regression testing, graded evals, and evidence audit trails in CI/CD

## [MVP] Environment & API Key Manager  (surface: public-api, effort: S)
Profile manager for Rainbird environments — Community (api.rainbird.ai), Enterprise (enterprise-api.rainbird.ai), South America (sa-enterprise-api.rainbird.ai), and private {client}-api.rainbird.ai / self-hosted URLs — with X-API-Key, x-evidence-key, and x-interaction-key stored in SecretStorage, never in workspace files. Integrators juggle dev/prod keys across hosting tiers today with nothing but env vars; this is the zero-config foundation every other feature authenticates through.
UX: A 'Rainbird' activity-bar container with an 'Environments' tree view. '+ Add Environment' opens a quickpick of base-URL presets plus custom URL entry, then password-masked input boxes for keys (stored via ExtensionContext.secrets; profile names/URLs in globalState). A status bar item shows the active environment and live engine version fetched from the unauthenticated GET /version. Context menu per profile: Set Active, Test Connection (probes a 401 vs 200), Copy Base URL. No config file is ever required — the anti-GraphQL/Apollo rule.
VSCode APIs: TreeDataProvider + window.createTreeView, ExtensionContext.secrets (SecretStorage), window.createStatusBarItem, viewsContainers/views contribution, commands + QuickPick
Inspiration: Neo4j for VS Code multi-instance connection manager + status-bar connection state; avoids Salesforce's CLI-dependency sprawl
Risks: Key scoping is user-level and opaque (403 = key lacks access); Test Connection needs a KM ID to fully validate, so a keyless /version probe is the fallback.

## [MVP] Decision Session Runner (question-loop debugger)  (surface: public-api, effort: L)
An interactive panel that drives the full Decisions API session lifecycle — GET /start/{kmID} (with version/useDraft/contextid options), POST /{sessionID}/inject, /query, /response, /undo — rendering each questionResponse exactly as the wire defines it and teaching the developer the protocol as they click. This is the integrator's core job (build the question loop into their app) made visible. Crucially, it can also ATTACH to an existing session by pasted sessionID — since inject/query/response carry security:{} in the OpenAPI spec, the sessionID is the credential — letting a developer take a session ID from their app's logs and continue or replay it live.
UX: Command 'Rainbird: New Decision Session' (or play icon on an environment) opens a webview panel. Left: session setup — kmID, version picker (live/numbered/draft), optional contextid, and an inject-facts JSON editor that warns at the 250-facts-per-request cap. Center: the conversation — question cards built from the questionResponse schema: markdown prompt, dataType-specific inputs (string/number/date/truth), knownAnswers and concepts[] as dropdowns, a certainty slider shown only when allowCF, an 'Unknown' button only when allowUnknown, yes/no buttons for 'First Form' questions, grouped extraQuestions rendered together, and an Undo button wired to POST /undo. Result cards show subject/relationship/object, certainty, and factID with an 'Inspect Evidence' button. Right: a collapsible raw wire log of every request/response JSON pair. A footer notes the 24h question-expiry window.
VSCode APIs: window.createWebviewPanel, webview postMessage/onDidReceiveMessage + CSP + asWebviewUri, SecretStorage (key retrieval), commands
Inspiration: SOQL Builder's form-that-round-trips-with-source + GraphQL Inline Operation Execution; Camunda Play as the 'watch it run' playground
Risks: Session TTL/expiry semantics are undocumented; attach-by-sessionID surfaces the fact that session IDs are bearer credentials — the UI must warn users to treat logged session IDs as sensitive.

## [MVP] Decision Request Files + Run CodeLens (.rbreq)  (surface: public-api, effort: M)
A convention-based, git-diffable text format for a decision run: a *.rbreq.json file holding {environment?, kmID, version|useDraft, inject[], query{subject?, relationship, object?}, answers[]?} validated by a bundled JSON schema. A 'Run decision' code lens executes it end-to-end and shows the result inline. This is the text-as-source-of-truth wedge: the exact API call your app will make, reviewable in a PR.
UX: Developer creates checkout.rbreq.json (snippet-scaffolded); the jsonValidation contribution attaches the schema so fields autocomplete and misspellings squiggle. Above the query block a code lens reads '▶ Run decision (staging)'. Clicking runs start→inject→query, applies scripted answers, and shows 'result: 82% certainty' inline plus a notification; if unscripted questions remain, it opens the Session Runner mid-session to finish interactively, then offers 'Save answers back to file'. Any session in the Runner can be exported as an .rbreq via 'Save as request file'.
VSCode APIs: languages.registerCodeLensProvider, jsonValidation contribution (bundled JSON schema), snippets contribution, window.showInformationMessage
Inspiration: Regal's Evaluate code lens with convention-based input.json discovery; MongoDB playground files saved alongside app code
Risks: Environment names in committed files must map to local profiles (never keys); needs a graceful story when a file references an environment the machine doesn't have.

## [MVP] Evidence Tree Inspector  (surface: public-api, effort: M)
Paste (or click through from a result card) a factID + sessionID and the extension recursively GETs /analysis/evidence/{factID}/{sessionID} with the stored x-evidence-key — the same fullEvidence() walk the JS SDK does — and renders the complete derivation tree. Integrators constantly need to answer 'why did my app get this result?' from nothing but IDs in their logs; today that requires hand-rolled recursive curl.
UX: Command 'Rainbird: Inspect Evidence'. A webview shows a collapsible tree: each node badge-coded by source enum (rule / knowledgemap / answer / injection / datasource / synthesis, mirroring Studio's color language), per-fact certainty, and for rule nodes a bindings table (%S/%O/variables) plus condition rows with impact and salience bars and wasMet flags; expression conditions expand to show functions, input facts, and computed result; alt evidence text renders as prose. Toolbar: 'Explain in English' (POST /nl/explain with language + optional style instructions), 'Open in Studio' (deep link [STUDIO_HOST]/evidence?id=FACT_ID&api=API_HOST&sid=SESSION_ID), 'Copy JSON', 'Export Markdown' for audit tickets. A legend decodes factID prefixes (WA:RF rule, WA:KF map, WA:AF answer, WA:IF injected).
VSCode APIs: window.createWebviewPanel, SecretStorage (x-evidence-key), env.openExternal (Studio deep link), env.clipboard
Inspiration: Regal's debug-adapter inspection ethos applied to a post-hoc artifact; HCP Terraform run-log sidebar
Risks: Requires x-evidence-key unless link-sharing was toggled on in Studio Publish — needs a clear fix-it message; deep recursion on large trees needs batching and cycle guards.

## [MVP] Copy-as-Code + SDK Snippet Library  (surface: client-only, effort: M)
Turns any Session Runner recording or .rbreq file into working integration code: TypeScript on @rainbird/sdk (with RESPONSE_TYPE_QUESTION/RESULT handling), plain Node fetch, Go on gitlab.com/rainbird-ai/sdk-go, and curl. Plus contributed snippets for the recurring patterns: session loop, 250-fact inject chunking, recursive evidence walk, sdk-react-material KitchenSink embed, /nl/interact call with the required 'Version: v1' header. Bakes in the trap knowledge: generated JS uses the SDK's 'cf' field while raw REST uses 'certainty', and Go codegen pins the documented enterprise-api.rainbird.ai URL rather than the SDK's conflicting EnvEnterprise constant.
UX: A 'Copy as…' button in the Session Runner toolbar and a context-menu item on .rbreq files opens a quickpick (TypeScript / Node fetch / Go / curl). Generated code reproduces the exact recorded flow with the API key referenced as an environment variable, never inlined. Snippets appear in JS/TS/Go files under prefixes like rb-session, rb-inject, rb-evidence, rb-kitchensink; hovers on rb- snippets document the cf-vs-certainty and enterprise-URL gotchas with doc links.
VSCode APIs: snippets contribution, env.clipboard, menus contribution (editor/context, webview toolbar), languages.registerHoverProvider
Inspiration: Postman-style code export; Prisma's polish standard for generated artifacts
Risks: Generated code must track SDK releases (@rainbird/sdk 1.5.x); templates need a version stamp so stale output is detectable.

## [MVP] Decision Regression Tests + Test Explorer  (surface: public-api, effort: L)
The 'regression test in CI' promise, shipped. *.rbtest.json files define cases (inject facts, query, scripted answers, expected results with certainty tolerance, or expected-questions assertions). A TestController discovers them, runs each case against a chosen environment and pinned KM version (the version param on /start makes runs reproducible; useDraft tests pre-release), and reports rich diffs. A scaffolding command emits a GitHub Actions workflow invoking the same runner headlessly (bundled as an npx-able script) with the key from repo secrets. Also imports Studio's Automated Tests JSON export as a starting corpus.
UX: Test Explorer shows 'Rainbird Decisions' with file→case hierarchy; run/debug icons in the gutter of .rbtest.json files. Failures render TestMessage expected/actual diffs including per-result certainty deltas ('expected 80 ±5, got 62'). 'Record test from this session' in the Session Runner writes a new case with the answers given and results received. Continuous-run (eye icon) re-executes on file save. Command 'Rainbird: Scaffold CI Workflow' writes .github/workflows/rainbird-tests.yml plus a package.json script.
VSCode APIs: tests.createTestController + TestRunProfile, TestMessage.diff, TestRunProfile.supportsContinuousRun, workspace.createFileSystemWatcher, tasks/ScaffoldCommand
Inspiration: OPA 'Run Tests in Workspace' + Apex Testing sidebar + Kogito SceSim scenario files; Rainbird's own Studio Automated Tests (JSON export/import) as the interchange format
Risks: Studio's automated-test JSON schema is not publicly documented — the importer is best-effort until Rainbird publishes it; billing note needed since production queries count on result-return.

## [MVP] MCP Endpoint Registration (served graphs into agent stacks)  (surface: undocumented-api, effort: S)
One command wires a served graph's MCP endpoint (from the rake.rainbird.ai research preview — Streamable HTTP, no auth header, the URL itself is the credential) into the developer's agent tooling: VS Code's MCP layer, Claude Code, or Claude Desktop. Because the URL grants access, the extension treats it like a password: SecretStorage by default, explicit warnings before writing it into a committable .vscode/mcp.json. This is the shortest path for the agent-stack integrator persona.
UX: Command 'Rainbird: Register Graph MCP Endpoint' prompts (password-masked) for the endpoint URL copied from the Served Graphs dashboard, validates its shape, and offers targets: (a) 'VS Code (recommended)' — registers via lm.registerMcpServerDefinitionProvider with an McpHttpServerDefinition resolved from SecretStorage so the URL never touches a file; (b) 'Workspace mcp.json' — writes .vscode/mcp.json after an explicit 'this URL is a credential' confirmation; (c) 'Claude Code' — runs `claude mcp add --transport http <name> <url>` in the integrated terminal; (d) 'Copy Claude Desktop connector JSON'. A 'Served Graphs' tree node lists registrations with the five tools (describe_graph, inject, query, answer, explain) and shows a fix-it hint when explain fails because the graph's Evidence Tree Link toggle is off (Studio → Publish → Live Version → API Management → Access Control).
VSCode APIs: contributes.mcpServerDefinitionProviders + lm.registerMcpServerDefinitionProvider (McpHttpServerDefinition), SecretStorage, window.createTerminal, TreeDataProvider
Inspiration: VS Code's vscode:mcp/install pattern and Prisma's MCP server shipping; mcp.json GA since VS Code 1.102
Risks: Research-preview surface: URLs can be paused/deleted from the dashboard at any time and the scheme may change before GA; never log or echo the URL; endpoint keeps serving the project's current version, so behavior can shift under a registered agent without warning.

## [MVP] Zero-Config Walkthrough + Sandbox First Run  (surface: public-api, effort: S)
A five-step walkthrough that gets an integrator from install to a real decision result in under a minute using the HelloWorld sandbox KM whose API key and KM ID Rainbird publishes openly in its docs — no account, no config file, no sign-in. Onboarding is where the comps separate 5-star from 2.5-star extensions.
UX: On install, the Getting Started page shows 'Ship your first Rainbird decision': (1) 'Run a sample decision' — one button fires the docs-published sandbox query (Tom → speaks → ?) and shows the result + certainty; (2) 'Add your environment' — opens the key manager; (3) 'Inspect the evidence' — opens the Evidence Inspector on the sandbox result's factID; (4) 'Copy it as code' — drops the TypeScript loop into a new editor; (5) 'Record a regression test'. Empty Environments view shows a viewsWelcome panel with the same entry points. Steps complete via completionEvents (onCommand).
VSCode APIs: walkthroughs contribution (completionEvents: onCommand), viewsWelcome contribution, commands
Inspiration: VS Code walkthrough UX guidance; Rainbird's own docs-published HelloWorld sandbox credentials make true zero-config possible
Risks: Sandbox key could be rotated by Rainbird — fetch IDs from a remotely updatable manifest with graceful degradation.

## [Phase 2] Graph Capability Explorer (describe_graph manifest viewer)  (surface: undocumented-api, effort: M)
Renders 'API docs for your decision service': every queryable relationship with its subject/answer concept types and question forms, askable vs inject-only distinctions, example subjects, and a key-concepts glossary. Two sources: (a) a local .rbird export — client-only, since .rbird is verified gzip-JSON containing the RBLang lines, parseable entirely offline; (b) the live MCP describe_graph tool for served graphs, which already generates exactly this per-graph capability manifest. Integrators usually receive a KM ID and nothing else; this tells them what they can actually ask.
UX: Command 'Rainbird: Explore Graph Capabilities' with a source picker (local .rbird/.rblang file, or a registered served graph). A panel lists each queryable relationship as a card: goal name, required inputs with dataTypes (string/number/date/truth), plural flag, question wording, inject-only warnings. Per-card buttons: 'Query in Session Runner' (prefills kmID + query triple) and 'Generate typed client'. Right-clicking a .rbird file in the Explorer offers 'Open Capability Manifest'.
VSCode APIs: window.createWebviewPanel, custom editor / context menus on *.rbird, workspace.fs (gunzip + JSON parse client-side)
Inspiration: Neo4j's connected-database-aware intelligence; Terraform module/provider explorer with doc links; the MCP preview's own generated per-graph doc proves the manifest is derivable
Risks: Live path depends on the MCP preview; local path can drift from the deployed graph version — surface the .rbird's version metadata and warn. There is no public REST endpoint for graph metadata (genuinely roadmap if Rainbird ever exposes one).

## [Phase 2] Typed Client Generation  (surface: undocumented-api, effort: L)
Generates a typed integration module from a graph's capability manifest: one function per queryable relationship with parameter and result types derived from concept dataTypes (string|number|date|truth; plural relationships → arrays), a typed question-callback interface for the ask loop, and results typed with certainty + factID. TypeScript output wraps @rainbird/sdk; Go output wraps sdk-go. A committed manifest lockfile makes regeneration diff cleanly in PRs — Prisma's schema→client loop applied to decision services, for developers who should never hand-type 'has annual income' as a magic string.
UX: From a Capability Explorer card or command 'Rainbird: Generate Typed Client': pick language and output path; the extension writes rainbird-client.ts (or .go) plus rainbird-manifest.json. A generated header comments the source graph, version, and generation date. On subsequent runs a diff preview opens before overwrite. If the workspace's manifest version mismatches the live KM version (checked via GET /analysis/session/{sessionID}?filter=version on next session), a warning diagnostic suggests regeneration.
VSCode APIs: workspace.fs + WorkspaceEdit, window.showTextDocument (diff preview via vscode.diff), languages.createDiagnosticCollection (drift warning)
Inspiration: Prisma generate + GraphQL codegen; the describe_graph manifest and local .rbird parsing are the schema sources
Risks: Client-only when generated from a local .rbird, undocumented-api when from describe_graph; no platform push/pull means drift detection is heuristic; RBLang parsing must handle undocumented elements (import, compound) without crashing.

## [Phase 2] NL Endpoints Playground (/nl/interact + /nl/explain)  (surface: public-api, effort: M)
A chat-style panel for the beta natural-language APIs that integrators building conversational frontends must tune: each turn POSTs /nl/interact (X-API-Key + required 'Version: v1' header) and exposes the parts a chat UI hides — the LLM-extracted query triple, the facts partitioned into injected/invalid/unmatched (the key debugging signal for fact-extraction misses), responseType routing, llmTokens usage, and suggestedChatResponse on errors. Results offer /nl/explain with the language and free-form instructions parameters exposed for prompt-tuning the narrative.
UX: Command 'Rainbird: New NL Session' opens a split webview: left is the conversation; right is the inspector showing, for the selected turn, the extracted {subject, relationship, object}, fact chips color-coded injected (green) / invalid (red) / unmatched (amber), and a running token meter. A lock badge appears while a query is active (one active query per session; new queries are ignored until a result unlocks it). An 'Explain' button on result turns opens a form for language (ISO 639) and instructions, rendering the narrative beside the raw evidence link.
VSCode APIs: window.createWebviewPanel, SecretStorage, webview messaging
Inspiration: MongoDB Copilot participant's NL-to-query transparency; Apollo's inline diagnostics ethos applied to fact extraction
Risks: Both endpoints are open beta with no SLA; facts are immutable within a session and the session-lock semantics need clear UI or users will think the panel is broken.

## [Phase 2] Integration Diagnostics (payload + SDK linter)  (surface: client-only, effort: M)
A diagnostics provider that catches Rainbird's documented integration traps before runtime, in both payload files (.rbreq/.rbtest/JSON bodies) and application code: inject arrays over the 250-fact cap (quick fix: chunk the batch), string values over 2,000 chars or containing the forbidden " ' \ < > characters, 'cf' vs 'certainty' field misuse for the target transport (SDK vs raw REST), the Go SDK's api-enterprise.rainbird.ai URL mismatch, missing 'Version: v1' header on /nl calls, first-form answers lacking answer:'yes'|'no', and — when a capability manifest is loaded — instance names not present in the graph, the exact 'accepted silently and attach to nothing' footgun the MCP preview doc warns about.
UX: Squiggles with explanatory messages and doc links appear in payload files and in JS/TS/Go source where SDK calls are detected (regex/AST heuristics). Each diagnostic ships a code action: 'Split into 2 inject batches', 'Rename cf → certainty for REST payload', 'Use enterprise-api.rainbird.ai (documented URL)'. A workspace-level 'Rainbird: Check Integration Health' command runs all checks and summarizes in the Problems panel.
VSCode APIs: languages.createDiagnosticCollection, languages.registerCodeActionsProvider, workspace.onDidChangeTextDocument
Inspiration: Regal's per-rule quick-fix code actions; Cedar's schema-based validation on open/save
Risks: Code-scanning heuristics must be conservative to avoid false positives in polyglot codebases; manifest-based instance checking is only as fresh as the loaded manifest.

## [Phase 2] Copilot Agent Tools (languageModelTools)  (surface: public-api, effort: M)
Registers VS Code language-model tools so Copilot agent mode can operate Rainbird directly without the MCP preview: rainbird_run_decision (environment + kmID + inject facts + goal → runs the full loop, surfacing unanswered questions back to the agent as structured output), rainbird_get_evidence (sessionID + factID → condensed derivation summary), and rainbird_list_capabilities (from a loaded manifest). Complements MCP registration: it uses SecretStorage-held API keys against the documented public API, works today for any published KM, and is #-referenceable in chat.
UX: After configuring an environment, agent-mode prompts like 'run the sanctions-screening decision for this applicant JSON and explain the result' invoke the tools; prepareInvocation shows a confirmation card naming environment, KM, and fact count (since production queries are billable on result-return). Tools appear as #rainbird references in the chat input. Results include factIDs that deep-link into the Evidence Inspector.
VSCode APIs: languageModelTools contribution + lm.registerTool, LanguageModelTool.invoke/prepareInvocation, toolReferenceName / canBeReferencedInPrompt
Inspiration: Prisma's Copilot agent-mode tools; VS Code's AI extensibility decision matrix (LM tools = agent mode + VS Code API access, MCP = cross-client)
Risks: Requires Copilot Chat infrastructure on the user's machine; agents can burn billable decision calls — confirmation UI and a per-session call budget are mandatory.

## [Phase 2] Interaction Timeline (production session forensics)  (surface: public-api, effort: M)
Fetches GET /analysis/interactions/{sessionID}?format=json (x-interaction-key) and renders the complete event log of a production session — start, inject, query, question, answer, result, and datasource events with timestamps — so an integrator can reconstruct exactly what their app and the engine said to each other. The polling-the-log pattern is Rainbird's documented alternative to webhooks, making this the only production observability surface integrators have.
UX: Command 'Rainbird: Open Interaction Log' prompts for a sessionID (or click-through from the Session Runner). A webview timeline lists events chronologically with type filter chips; datasource events show the relationship + certainty returned mid-inference; clicking a result event opens the Evidence Inspector on its factID. 'Export CSV' proxies format=csv. When the API returns empty/404, a fix-it panel explains that recording is off by default and must be enabled per KM version via 'Record Interactions' in Studio — and only sessions started after enabling are recorded.
VSCode APIs: window.createWebviewPanel, SecretStorage (x-interaction-key), env.clipboard / workspace.fs (CSV export)
Inspiration: HCP Terraform current-and-past-runs inspection inside VS Code
Risks: Useless until customers enable recording — the fix-it education is as important as the feature; large sessions need pagination/virtualized rendering.

## [Phase 3] Graded Evals + Audit Artifact Export  (surface: public-api, effort: L)
Extends the regression runner into the 'graded evals in your CI' capability Rainbird's pricing page markets but ships no tooling for: *.rbeval.json suites score decisions across a dataset (CSV of fact rows → injected per case) with certainty bands and per-case weights rather than binary pass/fail; runs produce a scorecard (pass rate, mean certainty drift vs the previous run, per-case deltas) plus JUnit/SARIF export for CI dashboards and an evidence-bundle export (zip of per-case evidence JSON + rendered Markdown) for auditors and expert sign-off — directly serving the regulated-industry buyers Rainbird targets. Execution uses only the public Decisions API; grading is client-side math. If Rainbird later ships a first-class evals/ModelOps API, this becomes its front-end.
UX: An 'Evals' node in the Rainbird view lists suites; 'Run Eval' executes cases in parallel against a pinned KM version with a progress notification, then opens a scorecard webview: headline pass rate, a certainty-drift column comparing the committed baseline (rainbird-baseline.json), and per-case rows linking to evidence trees. 'Export for CI' writes JUnit XML; 'Export audit bundle' writes the evidence zip. The GitHub Actions scaffold gains a --grade mode that fails the build below a threshold.
VSCode APIs: tests.createTestController (Coverage-style custom run profile), window.withProgress, workspace.fs (JUnit/SARIF/zip export), webview scorecard
Inspiration: OPA coverage toggle + the accelerators' 'run the evals locally' promise; fills the confirmed docs/marketing gap around 'Graded evals in your CI' and 'ModelOps'
Risks: The format of the accelerators' downloadable evals is unknown — alignment needed once visible; batch eval runs consume billable production queries, so dry-run against draft/useDraft must be the default; label stays public-api only because execution is, while any platform-native eval/ModelOps hooks would be roadmap.

## Journey: Embed a mortgage-underwriting decision in a Node service
A platform engineer at a bank SI receives a KM ID and a .rbird export from the customer's knowledge team. She installs the extension; the walkthrough runs a sandbox decision in under a minute, then she adds the bank's private {client}-api.rainbird.ai environment with its X-API-Key straight into SecretStorage — no config file, nothing in the repo. She right-clicks the .rbird and opens the Capability Explorer to see the queryable relationships and which facts are inject-only versus askable, then clicks 'Query in Session Runner' on 'qualifies for mortgage'. She injects applicant facts (the linter flags her 300-fact batch and offers to chunk it at 250), answers the two remaining questions the graph asks — noting the raw wire log to understand the questionResponse schema — and gets a result at 78% certainty. 'Inspect Evidence' shows a datasource-sourced credit fact dominating the salience. 'Copy as TypeScript' drops the full @rainbird/sdk loop into her service, key referenced as an env var. Finally she clicks 'Record test from this session', sets a ±5 certainty tolerance, runs 'Scaffold CI Workflow', and opens a PR where reviewers see the .rbtest.json diff — Rainbird's 'export, diff, review in a pull request, regression test in CI' promise, actually running.

## Journey: Wire a served graph into an agent stack
An AI engineer building a compliance agent gets an MCP endpoint URL from the Served Graphs dashboard. He runs 'Rainbird: Register Graph MCP Endpoint', pastes the URL into a password-masked input (the extension reminds him the URL is itself a credential and keeps it in SecretStorage rather than .vscode/mcp.json), and registers it into both VS Code and Claude Code via `claude mcp add --transport http`. In agent mode, his agent calls describe_graph to learn the queryable goals, then chains inject → query → answer. When the agent's explain call errors, the extension's Served Graphs view shows the fix-it hint: the graph's Evidence Tree Link toggle is off in Studio's API Management. Before shipping, he loads the capability manifest into Integration Diagnostics, which catches a misspelled instance name in his prompt templates — a value the graph would have accepted silently and attached to nothing. For the production path he also enables the Copilot LM tools, which run against the documented REST API with his real key, insulating the product from the MCP preview's churn.

## Journey: Production incident: why did we deny this claim?
A support escalation lands with only what the app logged: a sessionID and a result factID. The on-call integrator opens 'Rainbird: Inspect Evidence', pastes both, and the extension recursively walks /analysis/evidence into a full tree: the denial traces to an answer-sourced fact captured at 40% certainty, and an optional condition contributed 0% because a datasource returned nothing. The Interaction Timeline (recording had been enabled on this KM version) confirms the datasource event returned empty at 14:02. She clicks 'Explain in English' to generate an /nl/explain narrative for the customer response, and 'Export Markdown' to attach the audit trail to the ticket. Because session endpoints authenticate by sessionID alone, she then attaches the live session in the Session Runner, uses Undo to roll back the low-certainty answer, replays it with corrected input, and verifies the decision flips — root cause, customer communication, and verification without leaving the editor.

# CHALLENGE VERDICTS
- **SOUND** Environment & API Key Manager: Every claimed surface checks out against api.md: the four base URLs (api / enterprise-api / sa-enterprise-api / {client}-api.rainbird.ai plus self-hosted custom URLs), the three key types (X-API-Key, x-evidence-key, x-interaction-key), and unauthenticated GET /version (plain text, 4.118.0 today) are all confirmed. TreeDataProvider, SecretStorage, status bar and QuickPick are all stable APIs per vscode.md, and SecretStorage-not-workspace-files is the right hygiene given keys are user-scoped. Zero-config matches the anti-GraphQL/Apollo lesson in comps.md. Effort S is right for a tree + secrets + status bar.
